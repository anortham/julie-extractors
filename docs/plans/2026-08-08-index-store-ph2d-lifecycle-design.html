One maintenance namespace Public API

Chosen: `store maintain` contains inspect, gc, repair, and promote. Mutation requires explicit apply.

Planner then fenced apply Safety

Chosen: deterministic read-only reachability first; every apply revalidates roots, watermarks, CURRENT, and generation state.

Bounded in-place reclamation Capacity

Chosen: GC plus incremental vacuum handles normal pressure. Full repair and format work build a new generation.

Receipts before log pruning Recovery

Chosen: coordinator receipts preserve idempotency and request IDs; store logs are pruned only after the live request row is gone.

Generation-local pins Readers

Chosen: old readers renew in the old generation; retained-generation cleanup checks that generation's pins.

Forward rollback, no identity reuse Promotion

Chosen: rollback builds a new generation; family marks cover versions, logs, manifests, and resolution deltas.

Never touch

  • Protected roots — manifests, bases, identifier and pending deltas, bindings, pins, requests, scratch owners, cursors, rollback generations.
  • Serving generation in place — no full VACUUM, schema migration, or speculative immutable-row repair.
  • Legacy v3 contract — existing artifact commands and request-oriented store reports stay compatible.

Held constant

  • Retention defaults — 7 days, 1.20 target, 1.25 ceiling, 24 path history; roots and time window win.
  • Database split — store generations remain separate from root-owned coordination.
  • Release boundary — no push, tag, publication, or live Miller pin change without approval.

Verification gates

  • Correctness — randomized reachability and natural-row promotion equivalence.
  • Recovery — kill every catalog, filesystem, allocator, and CURRENT boundary.
  • Scale — bounded RSS, WAL, transaction time, and free-space refusal.
  • Compatibility — real old/current binaries and all supported languages.
