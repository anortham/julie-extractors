# julie-extract v2.40.0

classification: compatible

This release adds authenticated reader retention for shared family stores and
explicit WAL cleanup after standalone store writes. Extraction output contracts
are unchanged. Reader-enabled stores deliberately reject older writers.

## Reader retention

`store reader acquire`, `renew`, and `release` let consumers protect one immutable
snapshot before opening its generation database. Acquisition returns the exact
family, view, physical generation, manifest, and retained committed-log interval.
Retrying a lost acquire reply with the same owner nonce returns the same
registration instead of allocating another one.

Maintenance retains the registered manifest, its entries and referenced file
versions, physical generation, and required log history. Promotion does not
retarget an existing reader. Retirement refuses while the view has a protected
reader. A reader added or renewed after maintenance planning invalidates the old
plan. Reader registrations and consumer cursors remain separate contracts.

An expired heartbeat does not authorize deletion. Cleanup requires definitive
death of the original process instance. Paused live readers and unknown process
identity retain their roots. Authenticated release is idempotent. Reports bound
diagnostics and do not expose stored owner credentials or raw birth identity.

## Standalone WAL cleanup

Store write commands checkpoint both the generation database and coordinator
database after their final transactions close. A pinned reader can defer cleanup;
the command preserves its committed result and reports remaining cleanup work on
stderr. A later write, including replay or no-change completion, retries cleanup.
Read-only commands do not acquire this write behavior. This is not a hard WAL-size
cap: active read snapshots and large transactions can still retain WAL data.

## Compatibility and rollout

The extraction artifact remains schema 7, JSONL contract v5, extraction identity
epoch 9, and family store schema 2. The coordinator gains the reader catalog and
reader-capable families permanently require writer version 2.40.0 or newer.
Old 2.39 maintenance binaries refuse these families before mutation. Do not use a
writer downgrade override to bypass this protection.

Upgrade consumers and their bundled producer together. Only consumers that
register before opening and release after closing receive the new retention
guarantee; arbitrary direct SQLite readers cannot be made safe by this CLI alone.
Miller's M1 integration supplies that consumer lifecycle. Existing explicit legacy
export remains available; no automatic stale-artifact fallback is introduced.

The reader report is version 1. Acquisition is bounded metadata work and inserts
one registration, not a copied list of every file version. The measured 1k, 10k,
and 100k manifest fixtures each used ten store-data statements and zero full scans.
Those counts exclude first-time activation and maintenance's root enumeration.

## Verification and limits

- Producer Linux/Windows admission, liveness, retained-generation, rollback,
  maintenance, crash and mixed-version evidence:
  [reader-retention qualification](../evidence/2026-09-producer-retention-contract.md).
- Linux and Windows real-CLI WAL completion, held-reader deferral and retry:
  [WAL cleanup qualification](../plans/2026-09-05-wal-recurrence.md).
- Miller's source-built consumer tests cover all 40 supported languages, native
  admission/disposal, lost replies and concurrent maintenance on Linux/Windows.
  They do not replace verification against the published binaries.
- A failed maintenance cleanup can leave its bounded intent until expiry. Reader
  release then remains owed rather than bypassing the fence. The exact hidden
  destructor cleanup error is not yet exposed as a structured diagnostic.

No semantic runtime, model, or MCP tool is part of this release.
