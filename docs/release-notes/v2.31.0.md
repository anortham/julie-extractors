# julie-extract v2.31.0

Versioned family-store release. Julie can now build and maintain one durable store shared by
multiple views while preserving the existing standalone v3 artifact interface.

## Versioned store commands

- `store import`, `store update`, and repeatable-path `store delete` write immutable extraction
  versions through a durable coordinator. L1 becomes visible before bounded L2/L3 deepening.
- `store resolve` builds manifest-scoped immutable resolution bases and cumulative deltas without
  holding the store-writer lease for the whole-corpus pass.
- `store export` materializes one pinned exact view as a standalone v3 artifact.
- `store import --from-artifact` validates and imports a complete v3 artifact through resumable
  store transactions.
- `store maintain inspect|gc|repair|promote` exposes read-only planning and explicit `--apply`
  lifecycle mutations. Consumer cursors can be advanced or released through the same namespace.

Every request is idempotent by request ID and idempotency key. Store effects and request-global
chunk progress commit together; exactly one terminal store-log row makes a request committed in
fact. A successor resumes after the last committed chunk or reconciles a terminal store commit
without re-executing it.

## Lifecycle safety

The family root contains a separate `coord.db` plus immutable `gen-NNN` store generations selected
by an atomic `CURRENT` file. Promotion and forward rollback build, validate, checkpoint, fsync, and
rename a new generation before changing that pointer. Retired generations remain readable while
generation-local pins or the rollback safety window protect them.

GC is reachability-based and bounded. Current/historical manifests, ready resolution bases, both
delta tables, pins, live requests/claims, receipts, and consumer cursors protect their dependencies.
It demotes L3 before L2, purges only whole unrooted versions, archives terminal request identity
before pruning logs, and uses checkpoint plus incremental vacuum rather than an in-place full
`VACUUM`.

Root-owned family allocator marks keep file-version, store-log, per-view manifest, and per-view
resolution-delta identities monotonic across ordinary writes, promotion, and rollback. Maintenance
intent and writer-lease fencing prevent old processes or retired-generation handles from mutating a
new serving generation.

## Compatibility

- Legacy extraction contract 4, standalone SQLite schema 6, JSONL schema 4, and report schema 3 are
  unchanged from v2.30.0.
- The family store is a separate contract: store contract 1, SQLite schema 2, format epoch 1, and
  request/maintenance report schema 1.
- Store schema 1 development catalogs are refused before mutation; there is no in-place migration.
  This is the first published version of the family-store surface.
- Existing `scan`, `update`, `delete`, `info`, `export`, `languages`, and `rebind` behavior remains
  compatible.
- Miller does not consume the family store yet. Ph3 integration and the Miller pin bump occur only
  after this release is published and its downloaded assets are independently verified.

## Verification

The Ph2d dogfood used two views over all 38 supported languages, shared immutable versions, churn,
classified failures, exact resolution, pins, receipts, cursors, GC/demotion/purge, repair,
externally killed promotion with immediate recovery, forward rollback, and fresh-store comparison.
The final comparison matched 21 normalized visible groups per view with zero mismatches. Full facts
and timings are in
[the Ph2d dogfood record](../findings/2026-08-08-index-store-ph2d-dogfood.md).

The default, contract, crash, equivalence, strict Clippy, formatting, package-preflight, and local
archive/checksum gates are release requirements. Publication remains a separate approval action.
