# julie-extract v2.37.0

classification: compatible

This release fixes the queue defects behind a real incident: Miller submitted a
32 MB generated `parser.c` through `store update`, the coordinator accepted it,
and the resulting poison row made every later import on that family fail. Five
defects fed that failure. All five are fixed here, and an external adversarial
review of the change set confirmed the fix branch clean.

## Store update runs the scan discovery gate

`store update` used to read, hash, and enqueue any path it was given, including
files `scan` refuses. It now runs the same discovery decision `scan` runs,
before it reads the file. A refused file reports the terminal state
`unsupported` with a reason (`ignored`, `hard_excluded`,
`unsupported_extension`, or `oversized`), exits 0, and writes no queue row. The
report carries an additive `unsupported` object with the reason, the
root-relative path, and a message.

## The coordinator queue drains itself

- A request that outruns the quantum is requeued twice and failed on the third
  overrun with the `coordinator_quantum` error class. Before this, the
  coordinator measured the quantum after the work finished, threw the work
  away, and requeued the row on every drain, forever. One 29-second update
  starved every import behind it; deleting its rows by hand took a failing
  import from 28,670 ms to 17 ms. The overrun count lives in a new
  `quantum_overruns` column, added in place, and a contract test proves a
  migrated catalog is byte-identical to a fresh one.
- A drain reaps queued rows whose requesting process is dead and whose
  requester deadline has expired, and claimed rows whose claim owner is dead
  too. Reaped rows fail with the `coordinator_requester_dead` error class.
  Crash resume still works: a successor that replays the dead submitter's
  idempotency key adopts the row, so the reap can never take a row a live
  process is waiting on.
- `store maintain` now archives terminal request rows up to the log high-water
  mark instead of the consumer cursor, prunes aged failed rows, and reports the
  count as `pruned_request_rows`. One Miller family store had accumulated 2,163
  committed rows a lagging consumer pinned forever.

## Reports name their own request

A caller's report state now reflects only the caller's own request. Before,
one drain served the whole queue, so a backlog failure from someone else's
poisoned request could mark a committed import `failed`. Miller then throttled
a healthy store because the revision advanced on a scan its report called
failed. Backlog failures now arrive in an additive `warnings` array on the
import, update, delete, and from-artifact reports.

## `languages --json` publishes the discovery limits

The report gains a `discovery_limits` block: `max_source_file_bytes`, the
hard-excluded directory names, and the hard-excluded file suffixes, read from
the same constants the scanner uses. Miller mirrored these values as local
constants to avoid submitting files `scan` refuses; mirrored constants drift,
published ones cannot. The report schema stays 3, matching the precedent for
additive sections.

## Compatibility

Extraction output is unchanged: artifacts stay schema 7, JSONL stays contract
v5, family stores stay store schema 2, store format epoch stays 1, and the
extraction identity epoch stays 6. The coordinator's `requests` table gains the
`quantum_overruns` column through an in-place, fingerprint-identical migration,
so existing coordinator databases open without a rebuild. All report additions
are new optional fields; existing readers see the same JSON they saw in
v2.36.0 until a new condition occurs.
