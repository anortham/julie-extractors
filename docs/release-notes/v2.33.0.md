# julie-extract v2.33.0

Minor release that unwedges family stores whose batch work outran the writer lease, frees a store held hostage
by an abandoned resolve claim, and removes a per-page cost from store maintenance that could fail a GC run
outright. It also repairs three Windows-specific defects: process liveness was never known, `store import`
never retried a blocked drain, and a failed resolve leaked its scratch database.

## Long batch work is no longer rolled back at the quantum cap

Whole-repo `import` and `resolve` quanta may now outrun `maximum_quantum_ms` while the writer-lease heartbeat
keeps the lease alive, as from-artifact imports already could in 2.32.1. Previously such a quantum was rolled
back and requeued and the caller received a lease-lost error rendered as "store-writer lease fencing check
failed" — *after* the work had run in full. On a workspace whose store-import phase measures 71-85 seconds,
that meant the store could never converge and consumers' derived indexes stayed stale indefinitely.

Single-file `update` and `delete` stay capped on purpose: they are the interactive paths, and the cap is what
stops a long batch starving them.

## A single transient coordinator error no longer discards a scan

The writer-lease renewal thread previously treated the first unhappy renewal result as a lost lease: it
stopped renewing, the lease lapsed, and the commit's fencing check then rejected everything the executor had
just done. One momentary `SQLITE_BUSY`, or one renewal tick arriving late because the thread was starved
behind the extractor's own worker pool, was enough — and it bit hardest under load, exactly when scans are
slow.

Renewal now retries a transient failure, and re-extends a lapsed row only when it still carries this holder's
fencing token, which proves no takeover occurred. The retry backoff is capped by the renewal interval so the
retry ladder can never outlast the lease it is defending.

## An abandoned resolve claim no longer wedges the family

`uidx_coord_one_claimed_resolve` permits at most one claimed resolve per family. A `resolve` request left
`claimed` by a process that exited — an interrupted CLI, for example — therefore blocked *every* later resolve
in that family permanently: the store could not leave `resolution=unbound`, derived indexes never converged,
and `store gc` and `store repair` were refused as well, because both refuse while any request is claimed. The
repair verb could not repair it; recovery meant editing the coordinator database by hand.

The eligibility rule that frees such a claim — a stale heartbeat, or an owner PID known to be dead — already
shipped, but was only ever evaluated for the request being claimed, never for the request doing the blocking.
It is now applied consistently. An abandoned blocker is reaped to `failed` with an `error_json`, which is a
terminal state, so `store gc` can also reclaim its resolution scratch.

A live holder is unaffected: a running resolve refreshes its claim heartbeat every 250 ms against a 5 second
staleness window.

## Dead-lease takeover requeues instead of adopting

Taking over a dead holder's writer lease used to re-stamp that holder's in-flight requests with the new
holder's id and a fresh heartbeat. The new holder never executes a request it did not submit, so such a row
stayed claimed forever, and because each later takeover refreshed the heartbeat again, the staleness steal
could never fire either. Those requests are now requeued, so the next drain re-claims and re-executes them.

## Incremental vacuum reclaims its whole page budget per call

`PRAGMA incremental_vacuum(N)` yields a row for each page it reclaims, and was being stepped exactly once per
call. The page-budget argument was therefore inert — one call freed one page — and the surrounding loop paid a
separate implicit write transaction, and an fsync under `synchronous = FULL`, for every single page.

Reclaiming 4,608 pages took 11.3 seconds of an 11.5 second maintenance apply, which by itself outran the 5
second writer lease and failed the run with a lease-lost error at the end. Release builds were no better: the
cost is serialized fsyncs, not optimizable work. Draining the statement makes the reclaim a single
transaction. The covering contract test went from failing after 23.70 seconds to passing in 0.55 seconds.

The same fix applies to the generation repair path, which reclaims pages the same way.

## Windows: process liveness is now known, not assumed

The coordinator's process probe returned "unknown" for every PID on Windows, so a crashed holder was never
provably dead there. Both reclaim paths above test "the timer expired OR the owner PID is dead", so they
still fired on Windows — but only through the timer, after the full five second staleness window, never
immediately on the evidence that the owner was gone. A working Windows probe already existed in this
repository, in the export path, and simply was not used by the lease path.

There is now one probe, in the artifact crate, and the export path and the parent watchdog both call it. It
resolves a PID through `tasklist`: a matching row means alive, no matching row means dead, and a probe that
cannot run reports unknown, which every caller still treats as alive.

A `tasklist` call costs about 100 ms on the measured host, and the lease paths probe from retry loops that
tick every 10 ms, so the Windows probe reuses each result for 250 ms. A caller blocked on a lease therefore
cannot spawn a process per tick, and the only cost is that a process which exits reads as alive for at most
that window — well inside the five second lease.

## `store import` retries the drain instead of waiting out its budget

`store import` attempted the drain once. If the writer lease was held elsewhere it dropped into a wait that
only watched for somebody else to finish its request — so when the lease was released without that request
being executed, which is the crash-resume case, nothing ever retried. The request ran out its whole budget
and exited 1 with `failure_class: request_timeout`. A lease measured free after 4.95 seconds still cost a
119 second wait.

The drain is now retried, matching `update`, `delete`, and `from-artifact`. A retry inherits the original
requester deadline, so a resumed request gets what remains of the crashed process's window rather than a
fresh one. In the covering test, an import blocked by a lease released after 500 ms went from a 30 second
timeout failure to committing in 1.1 seconds.

## A failed resolve no longer leaves its scratch database behind

`ResolutionBaseWriter` and `ResolutionScratchWriter` unlink their scratch files when dropped without a
successful finish. Both hold their SQLite connection in a struct field, and Rust runs the drop body before it
drops the fields, so the database was still open at the unlink. On Windows SQLite opens files without
`FILE_SHARE_DELETE`, so every one of those deletes failed, and the failure was discarded. Orphaned
`resolve-*.db` files accumulated after each failed resolve, and a partially written file marked
`completed=0` survived. POSIX permits unlinking an open file, which is why this never showed on Linux.

Both writers now close the connection before unlinking, an idiom already used elsewhere in the same file.

## Compatibility

The versioned store remains schema v2 and format epoch 1. Manifests, resolution bases, the standalone v3
artifact, resolver-output epoch, crash boundaries, publication identity, and CLI report contracts are
unchanged.

Two observable coordinator behaviors change, both deliberately. A resolve request abandoned by a dead owner
now becomes `failed` with an `error_json` rather than remaining `claimed` indefinitely. A dead holder's
in-flight requests become `queued` on takeover rather than being adopted as claimed.

A third change is Windows-only and follows from the working liveness probe: a reclaim that previously had to
wait out a staleness timer there now fires as soon as the owner is known to be gone.

## Verification

`store_coordinator_contract` passes 62/62 both serialized and under full parallelism, across five consecutive
parallel runs. `store_maintenance_contract` passes 19/19 on Windows — the harness declares 20 tests and one is
`#[cfg(unix)]`. Formatting is clean, and the strict Clippy gate CI runs
(`--workspace --all-targets --all-features --no-deps -- -D warnings`) passes on Linux, which is the platform
CI runs it on.

That same gate does not pass on Windows, and did not before this release either. Three `#[cfg(unix)]`-only
bindings in the artifact crate's tests were unused there and are now guarded. Three more remain in the CLI
crate's feature-gated test targets and are left for separate work, because one of them changes what runs:
`store_operations_contract.rs:8` has unused imports, `store_maintenance_performance.rs:34-35` has unused
bindings, and `store_resolution_adapters.rs:1494` and `:1503` call `std::os::unix::fs::symlink` with no
`cfg` guard, so that whole test target fails to compile on Windows rather than merely linting.

Five tests cover the three Windows repairs, each verified to fail before the fix and pass after:
`process_status_separates_a_live_process_from_an_exited_one` and
`windows_process_status_is_correct_again_once_its_cached_result_expires` for the probe and its cache;
`import_drains_as_soon_as_a_blocking_lease_is_released` for the drain retry, which went from a 30 second
timeout failure to committing in 1.1 seconds; and
`dropping_an_unfinished_base_writer_removes_every_scratch_file` plus its scratch-writer twin for the unlink
order.

Serialized, the `store_resolution_contract` suite improves from 6 failures to 4 on Windows. The two that
start passing are the crash-resume pair, which is what a working liveness probe unblocks. That suite is
unstable under parallelism on Windows both before and after this release — three runs at the previous commit
gave 5, 10 and 6 failures — so only the serialized run is treated as evidence.

The remaining Windows failures are pre-existing test defects, not product defects: a test that shells out to
`sh`, a test that asserts the documented Unix-only `--parent-pid` watchdog fires, a spool test that fails in
its own setup, and `store_resolution_adapters.rs`, which calls `std::os::unix::fs::symlink` with no `cfg`
guard and therefore cannot compile on Windows at all.

Three coordinator contract tests were also made deterministic. Each asserted scheduling or ordering behavior
while implicitly depending on a real wall-clock writer lease that every other clock in the test replaced with
an injected one, so on a loaded host they failed having tested nothing they were written to test.
