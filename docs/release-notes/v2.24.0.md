# julie-extract v2.24.0

Cold-scan performance release. On the dotnet/runtime yardstick (41,406 indexed
files, 12.86 M identifiers) the same `scan --jobs 4` that took 76.3 minutes on
v2.23.1 completes in ~24 minutes with an artifact 2.4 GiB smaller — measured
3.2–4.1× run-to-run — with byte-for-byte identical row counts and resolution
outcomes. Two root causes found by live profiling, one by a two-repo index
audit.

## Memory-aware bulk cache

The bulk connection's page cache was a fixed 128 MiB against multi-GiB
artifacts; profiling showed the resolution phase ~90% blocked in `pread`/
`pwrite` on b-tree page churn. The cache now sizes to an eighth of physical
memory, clamped to [512 MiB, 8 GiB], probed without `unsafe` (procfs on Linux,
`sysctl` on macOS, PowerShell CIM on Windows; probed once per process; a failed
probe gets the 512 MiB floor). `JULIE_BULK_CACHE_KIB` overrides the policy
verbatim (SQLite semantics: negative = KiB, positive = pages). This change
alone measured 76.3 → 47.0 minutes.

## Savepoint-free bulk resolution

With the cache fixed, `memjrnlTruncate` was ~82% of remaining resolution
samples: the whole-pass `SAVEPOINT resolution_hook` inside the bulk-load
transaction (`journal_mode = MEMORY`) forced a pre-image of every bulk-loaded
page into the in-memory journal, and each batched-flush statement end truncated
that journal by walking its chunk list — quadratic at 10 M+ identifiers (the
v2.9.0 `ResolutionWriteBuffer` batching bounded statement-ends for that era's
scale, not this one). A bulk FIRST BUILD now runs the resolution hook without
the savepoint; measured 47.0 → 18.8 minutes on top of the cache fix.

Failure semantics on the bulk path change deliberately: a resolution hook error
aborts the whole scan with the new `BulkResolutionFailed` write error (CLI
report: `db_write_failed`, message names the resolution error and says to
rerun), and the empty first build rolls back — there is nothing durable to
protect, which is exactly why the savepoint bought nothing but the quadratic.
WAL delta paths (single-file updates, deletes, in-place rescans) keep the
savepoint and the contained "scan commits, rows stay unresolved" semantics
unchanged.

## Three secondary indexes retired

A two-repo consumer audit (every SQL statement in julie-extractors and Miller
touching `identifiers`/`reference_sites`, then `EXPLAIN QUERY PLAN` for each
shape) found three indexes no query ever selects:

- `idx_identifiers_path`
- `idx_identifiers_file_line_name`
- `idx_reference_sites_span`

Together 2.43 GiB (~11%) of a dotnet/runtime-scale artifact plus their share of
bulk-load index-build time. They are dropped from the schema and existing
artifacts shed them on their next open (idempotent `DROP INDEX IF EXISTS`; the
freed pages are reused rather than returned until the artifact is rebuilt or
vacuumed). No schema-version bump: index presence is not part of the data
contract, and the v5 catalog authority is regenerated.

Two further audit candidates were retained on purpose:
`idx_identifiers_reference_site` and `idx_reference_sites_containing_symbol`
back foreign-key cascade/SET NULL child searches that no query plan surfaces —
the schema-contract FK guard caught exactly this.

## Contract changes

- New `ArtifactWriteError::BulkResolutionFailed { message }`, surfaced by the
  CLI as `db_write_failed` with `resolution_error` in details. Bulk-path-only.
- SQLite catalog: three indexes removed (see above);
  `docs/contracts/sqlite-schema-v5.catalog.sha256` regenerated. Table shapes,
  row contracts, and the JSONL export are unchanged.
- No new CLI flags. `JULIE_BULK_CACHE_KIB` is an operator escape hatch, not a
  contract surface.

## Evidence

Branch gates at the released tree on rustc 1.97.1: `cargo fmt --check`, clippy
`-D warnings` (workspace, all targets), `cargo test -p xtask`,
`cargo xtask test default`, `cargo xtask test contract` (87). Writer contract
55 tests including two new bulk-resolution tests watched against the prior
semantics; schema contract 16 including the FK leading-index guard.
End-to-end validation on dotnet/runtime with production defaults: identical
row counts across all 24 domains, identical resolution
outcome/tier/method aggregates and pending counts, retired indexes absent,
artifact 22.84 → 20.41 GiB, wall 76.3 → 23.7 minutes on the same box and argv.
