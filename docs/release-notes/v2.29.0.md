# julie-extract v2.29.0

Row-level resolution scoping release: an incremental save now re-resolves the
reference rows its change can actually reach, instead of every row in every file
that merely mentions a touched name. One change, in the resolution pass, with no
schema change, no artifact-contract change, and byte-identical output.

## A one-file save selects rows, not files

Delta resolution ran each sweep as two merged worklists: a by-names arm that
selected individual rows, and an in-files arm that swept whole files. The file
set was the amplifier. It unioned every file declaring a touched type and every
file importing a touched name, because two keying relations — an import's
aliased `imported_name`, and a receiver's resolved type — are names that no
reference row spells out in the columns the worklists match on, so the only way
to reach those rows was to sweep the files holding them.

Measured on a 381k-identifier C#-dense workspace, that union made a single-file
save re-derive **80–87% of the workspace's identifier rows** and cost 16–18 s,
while the names the save actually touched bore about **1.6%** of them.

v2.29.0 expands the *name set* through those two relations instead of expanding
the file set. `delta_scope_files` now returns three fields:

- `recheck_names` — the touched names, plus both sides of every import either
  side of which is touched, plus the names of the symbols whose resolved type is
  touched. One round of expansion, not a fixpoint: a name reachable only through
  a name that was itself reached cannot key a row against the touched set.
- `recheck_files` — only the changed files and the module-candidate importers.
  The module re-point class binds by PATH existence, so no name can select it and
  it keeps whole-file recheck over its small file set.
- `selected_row_files` — the files holding every row either arm selects. The
  locator, the covered set and the ownership read are built from this, because a
  file the locator never loaded answers `None` and would silently drop a
  co-location join for a row the name arm did select.

The worklist SQL is unchanged, the sweep order is unchanged, and every buffered
write flush point is unchanged.

### Measured save-shape A/B

A one-file save on an identifier-dense C# workspace now re-derives **4.8–14x fewer
resolution rows**, cutting the measured save from **16.0–18.7 s to 6.4–10.8 s**.

Method: macOS (Darwin 25.6.0, Apple Silicon), release binaries, the full Miller
repo as fixture (~376k identifiers). The base artifact was built once by the OLD
binary (`scan --jobs 4`, 18.4 s); each measured save appends one newline to the
target file and runs `update` against a fresh clone of that base. Three runs per
binary per file. Old = pinned v2.28.0; new = the row-scoped build.

Wall clock below is the **median** of the three runs — the evidence files carry
every individual run. `identifier_resolutions` was identical across all three runs
of each arm.

| File | Binary | Wall (median) | Rows re-derived | `pending_resolutions` |
|---|---|---:|---:|---:|
| `src/Miller.Indexing/JulieExtractRunner.cs` | v2.28.0 | 16.0 s | 339,869 | 110 |
| | **v2.29.0** | **6.4 s** | **24,353** | 110 |
| | | **2.49x faster** | **13.96x fewer** | unchanged |
| `src/Miller.Server/Tools/SearchTool.cs` | v2.28.0 | 18.7 s | 348,980 | 287 |
| | **v2.29.0** | **10.8 s** | **72,329** | 287 |
| | | **1.73x faster** | **4.82x fewer** | unchanged |

Against the committed baselines — 90.3% of identifier rows for
`JulieExtractRunner.cs` and 92.7% for `SearchTool.cs` — a save now re-derives about
**6.5%** and **19.2%** of the corpus respectively, saving 9.6 s and 7.9 s.

**`pending_resolutions` is identical old-vs-new on both files** (110 and 287). That
is an equivalence signal from the production path, independent of the test suite and
pointing the same way as the 40-save zero-mismatch dogfood below: the new selection
re-derives far fewer rows while producing the same pending outcomes.

Three things this table is honest about:

- **Rows and wall move by different factors, and the rows number is the one this
  release earned.** The row cut is 4.8–14x; the wall win is only 1.7–2.5x, because
  once the amplification is gone the fixed costs dominate: extraction, the artifact
  write, and the whole-workspace candidate-index load. Narrowing that index is the
  named follow-up lever — a direction, not a promise.
- **The win depends on how hot the touched names are.** `SearchTool.cs` still
  selects 19.2% of the corpus, because the names it touches are widely used, while
  `JulieExtractRunner.cs` selects 6.5%. Row scoping removes the *file*
  amplification; it does not make a genuinely hot name cheap. A save's cost now
  tracks its own reference footprint, which is the point, but that footprint is not
  uniformly ~1.6%.
- **No resolution-phase figure is claimed.** The probe measured end-to-end `update`
  wall clock; the verb's JSON report exposes no resolution phase key, so the split
  between resolution and the fixed costs was not captured and is not estimated here.

The honest floor: `load_index` is still a whole-workspace load (~2.5 s at 120k
identifiers) and this release does not change that, so a save does not become
sub-second. What this release removes is the row amplification on top of that floor.

## A correctness repair on the scoped path

One selection key does not fall out of the workspace: the pending recheck deletes
its co-located identifier's overlay row, and that identifier is named after the
pending's terminal name — a key no workspace-keyed recheck carries — so
`recheck_resolved_pending_items` now reports what it demoted and the fill sweep
re-derives exactly those ids, name-selected and id-filtered so the ownership read
stays sound.

## Shadow mode

`JULIE_RESOLUTION_SHADOW=1` runs the legacy file-scoped scope computation first,
inside a nested savepoint rolled back before the real pass writes, then runs the
row-scoped path for real and diffs the two overlays row-for-row on their natural
keys (`pending_resolutions`, `identifier_resolutions`,
`identifiers.target_symbol_id`, ignoring `resolved_at_revision`). A mismatch
writes a JSON report to stderr naming the table, the key and both values, capped
at 50 spelled-out differences with the total count always reported.

- Off by default. The switch is read once per pass and only from the
  non-promoted scoped-delta branch, so a full or promoted pass never touches the
  environment and an unset switch costs one `getenv`.
- `JULIE_RESOLUTION_SHADOW_INJECT=<identifier_id>` is a TEST-ONLY companion, read
  only when shadow mode is on. It stamps a sentinel over that key in the captured
  in-memory snapshot — never in the artifact — so the mismatch path can be proven
  to fire.
- **New CLI surface: a shadow mismatch forces exit code `4`.** `4` was previously
  unused. It is deliberately not `3`, which the CLI already returns for the
  compatibility refusals (`schema_migration_required`, `schema_incompatible`,
  `contract_incompatible`, `fingerprint_mismatch`, `no_committed_revision`) — so a
  harness that keyed on `3` would misread a version refusal as a scope divergence.
  With `4`, "the two paths disagreed" is distinguishable from every live code by
  exit status alone; the stderr JSON report stays the authoritative signal.
- A mismatch cannot ride the resolution hook's error type — the writer catches
  that, rolls the overlay writes back and still exits zero, which would lose both
  the non-zero exit and the write. So the hook records the mismatch and `main`
  adopts the code after the commit completes. **The write still lands.**

### Dogfood

40 shadowed saves across two real repos (the julie-extractors Rust crates corpus
and the Miller C# `src` corpus): 28 content touches and 12 renames, run against
the release binary with `JULIE_RESOLUTION_SHADOW=1`. **40 of 40 exited 0 with
zero bytes on stderr — zero mismatches.** Renames are first-class here, since
`touched_symbol_names` unions inserted names with the OLD names collected before
deletion, and a rename is the case that must re-derive rows under both.

## The crossover sweep, re-measured

`DELTA_SCOPE_CROSSOVER` stays **0.7**, and the single-changed-file exemption
stays. Neither was adjusted; both were re-checked.

The sweep's x-axis was written for v2.28.0's widened FILE scope, which row
scoping deleted, so it was re-derived against what the guard now weighs: rows in
`recheck_files` plus rows matching `recheck_names`. Re-measured on the 2000-file /
92k-identifier fixture (release, FULL baseline 659 ms), the crossing — where a
scoped pass stops being cheaper than one Full pass — sits at **90.4% of selected
rows**, so the shipped 0.7 sits below it with *more* margin than the 80% it was
checked against in v2.28.0.

Two honest caveats:

- The wall-clock curve barely moved (0.07x / 0.37x / 0.97x / 1.08x / 1.33x against
  v2.28.0's 0.07x / 0.37x / 0.96x / 1.08x / 1.37x). That fixture's touched names
  are each declared in exactly one file, so the file unions row scoping removes
  were already proportional to N there. The synthetic sweep cannot show the
  amplifier; the save-shape A/B above is where the win is measured.
- The guard sums both arms and counts a row both arms select twice, which
  overstates the share and so promotes *earlier* than nominal. On that fixture a
  0.70 selected share corresponds to a true row share near 62%, where a scoped
  pass still runs at roughly 0.8x FULL. That costs time and never correctness — the
  same direction the threshold already errs in — and the recorded fix is a
  de-duplicated count, left as a follow-up rather than a threshold change.

## Compatibility

- No schema change, no artifact-contract change, no new flags, no new columns or
  indexes.
- `RESOLUTION_VERSION` is unchanged (still 6). For any corpus state, a row-scoped
  delta produces the same overlay rows as the file-scoped path did — the same
  `pending_resolutions`, `identifier_resolutions`, and
  `identifiers.target_symbol_id`. Delta and Full remain contracted to agree
  (`resolution_scope_equivalence`).
- Full passes are untouched: the change is confined to how a scoped delta selects
  what it re-derives.
- The only new observable behavior is opt-in: the shadow mismatch exit `4`,
  reachable only when `JULIE_RESOLUTION_SHADOW=1` is set. With the switch unset,
  every exit code means exactly what it meant in v2.28.0, and no existing code
  changed meaning.
