# julie-extract v2.33.2

v2.33.2 is the current published release. This is a Windows reliability release. Every change here came
from one investigation: resolves that failed with `resolve claim lost` while nothing was actually wrong
with the claim, plus two correctness regressions found while closing that path.

## The coordinator opened two databases for every construction

`StoreCoordinator` held no connection. All 27 of its methods opened a new `coord.db` connection and
re-ran the full writer pragma set, and the resolve claim heartbeat did that four times a second for the
whole life of a resolve. Constructing a coordinator also opened `store.db` to read the family id.

SQLite raises `SQLITE_PROTOCOL` ("locking protocol") from its WAL read-transaction retry ladder after
WAL-index recovery, and recovery is driven by the open-connection count reaching **zero**: the last
connection out checkpoints and unlinks `coord.db-wal` and `coord.db-shm`, and the next open rebuilds
them underneath every other reader. `open_coordinator` reported that transient condition as a corrupt
coordinator, and callers reported it as a lost claim.

This was never a race between two writers. It was one process cycling its own database fast enough
that SQLite gave up.

The coordinator now holds one connection for the life of the instance. Three paths still open their
own on purpose, because they need a connection while `self` is already borrowed and `Connection` is
not `Sync`: the `LeaseReleaseGuard` drop path, and the drain's lease-heartbeat thread.

Holding the connection did not remove every open: the resolve claim heartbeat runs in its own thread
and builds its own coordinator, because it needs a connection while the caller already holds one and
`Connection` is not `Sync`. Those opens could still land on a moving WAL index. Building a coordinator
opens two databases — `coord.db` for the coordinator itself, then `store.db` to read the family id —
and both now retry a locking-protocol failure a bounded number of times. The same read-only retry
covers the store read in `reconcile`, `ensure_writer_eligible`'s complete store-metadata validation
before lease acquisition, the resolution base and scratch readers, and the `open_reader` path in
`connection.rs`. SQLite opens lazily, so the retry wraps the first read as well as the open.
That is correct because the condition is transient; reporting it as a corrupt coordinator was always
wrong. The retry is deliberately absent from writer/lease mutation paths, including `open_writer` and
lease validation. It is only affordable because these opens are now rare; on the old per-call path it
would have sat inside the five-second claim window and could have burned the claim it was protecting.

An earlier measurement on the store resolution contract suite put the coordinator-reuse pass at
about **45 seconds**, down from about **90**. That is a historical performance measurement; the exact-tree
release-prep gate evidence is recorded below.

## Lease acquisition and renewal now use the real owner and clock

`try_acquire_or_takeover` used to sample wall time before `BEGIN IMMEDIATE`. If SQLite waited for a
busy coordinator, the five-second expiry was already partly or completely spent when the transaction
started; the immediate renewal could then report a lost lease even though acquisition had just
returned `Acquired`. The production acquisition path now samples wall time after `BEGIN IMMEDIATE`
succeeds. Deterministic logical-time callers retain their injected clock.

`with_writer_lease` used to renew once on acquire and then run the whole operation with no further
renewal. The candidate renews while the operation runs and stops the heartbeat before release so it
cannot race the release. Renewal retries transient coordinator errors and may reclaim a lapsed row only
when the fencing token is still ours. A successor's token makes renewal return false immediately; a
busy or locked coordinator no longer silently ends the heartbeat.

## A busy database was read as a stolen claim

The claim heartbeat treated any coordinator error as proof that another resolver had taken the claim,
so the first transient error killed a resolve that still held it. Errors are now retried within the
heartbeat tick; only `Ok(false)` after the token-checked renewal path confirms an actual loss. The error
message names the real cause instead of guessing.

## A single changed path was promoted to a full resolution

The delta planner's name arm can select many identifier rows outside the changed file. A regression
then let that broad result promote a **single-changed-file** request to a full resolution, undoing the
single-file exemption that keeps local edits scoped. The candidate restores the exemption: one changed
path remains scoped even when its name arm selects every identifier row. On the old live behavior, that
mistake took **182,867 ms** and produced **549,149 rows**; those are historical measurements of the
wrong full path, not a v2.33.2 gate result.

## Windows diagnostics and verification guards

Report diagnostics joined a root with a root-relative path using `Path::join`, which inserts the
platform separator. On Windows that produced `/repo\scripts/install.ps1` — one string carrying both
separators, from a contract that specifies `/`. The relative side is always `/`-separated, so the
separator between the two sides is now written explicitly.

The Windows store-resolution gate runs the feature-enabled 24-test contract target serially with
`--test-threads=1`. The repeat harness requires the feature and asserts that 24 tests ran; without
those guards Cargo can report a false green result after running zero tests. The contract tests also
print a failing child command's output and detect a child that exits before reaching its fault-injection
point. Without those checks, the main defect reported itself only as "timed out" and stayed invisible.

Three Windows test defects are also fixed: a spool test set a timestamp through a read-only handle,
which Windows refuses; and two import tests asserted Unix-only `--parent-pid` supervision on every
platform, when the flag is documented as accepted and ignored elsewhere so one caller argv works
everywhere.

## Release-prep verification

The exact tree passed the release-prep gates on 2026-08-13: `cargo fmt --all -- --check`,
`cargo test -p xtask`, `cargo xtask test default` (exit 0 in 96.6 seconds), and `cargo xtask test contract`
(exit 0 in 713.2 seconds, including the serial feature-enabled 24-test resolution target, which passed
24/24 tests in 101.54 seconds). Strict workspace
`cargo clippy --workspace --all-targets --all-features --no-deps -- -D warnings` also passed.
`cargo xtask release preflight --version 2.33.2` validated 4 targets and 32 inputs, and
`cargo xtask release package-list` passed. `git diff --check` passed. These are source-tree gates;
the v2.33.2 source push and live release assets have since been verified.

## Compatibility

No contract moved. Schema, SQLite store schema, extract contract, report schema, and the hash
algorithm are unchanged from 2.33.1, so consumers need no work to adopt this release.
