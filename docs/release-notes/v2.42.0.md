# julie-extract 2.42.0

classification: compatible

This release makes family-store imports and exports faster and makes store lock
and integrity reporting explicit. Extraction output, schemas, and the
extraction identity epoch are unchanged.

## Import and export throughput

- Deep-wave prefetch: while the coordinator writes one deep chunk, a spawned
  thread extracts the next chunk on the shared worker pool. A prefetched
  result is used only when its request id, chunk index, payload hash, and the
  source file's modification time and size all still match; otherwise the
  chunk extracts inline. The first deep chunk always extracts inline, so a
  source change at the L1 publish boundary still fails as
  `changed_between_waves`. Interactive updates extract on their own pool.
- The drain keeps one fenced store writer connection across quanta and
  revalidates the generation fence and writer lease before each quantum, so
  the bulk page cache survives across chunks. The executor keeps its worker
  pool instead of building one per quantum.
- `--jobs 0` now resolves to four fifths of the available cores with a floor of
  one. A new import freezes a deep chunk of `max(8, workers)` files so every
  worker has a file in each deep quantum. Requests written before this release
  still read as 100 L1 and 8 deep versions per quantum.
- The bulk writer applies a memory-sized page cache and in-memory temp store,
  reuses one in-memory staging schema per quantum for L1 projection checks,
  and export uses cached inserts with the same cache.
- Measured on this repository (2,316 extractable files, 24 cores): fresh
  `store import --level full` 55 s to 28 s, `store export` 43 s to 23 s, peak
  memory unchanged. Details:
  [performance audit](../findings/2026-09-08-performance-audit.md).

## Store reliability and reporting

- Bundled SQLite advances to 3.53.2 (rusqlite 0.40.2, libsqlite3-sys 0.38.2),
  which carries the WAL-reset fix. A contract test fails if the bundled SQLite
  ever predates it.
- Store commands wait up to five seconds for a locked store database on open.
  A lock still held after that is class `busy` with code `store_busy` when it
  blocks the store open, or `maintenance_busy` when it blocks a quick check.
- `store maintain inspect` and `repair` run `PRAGMA quick_check` on the store
  and coordinator databases before planning. Their check list adds
  `store_quick_check` and `coordinator_quick_check`; a failed report keeps the
  checks that ran, and corruption reports `integrity_failed` with code
  `integrity_check_failed`.
- A committed import report now survives a successor writer that starts before
  the report projection, instead of failing with `database is locked` after a
  durable commit.

## Compatibility and rollout

- Artifact schema remains 7, JSONL export contract remains v5, report schema
  remains 3, and family-store schema remains 2. Extraction identity epoch
  remains 10, so unchanged files are not re-extracted.
- The deep chunk progress event in `store_log` gains a `prefetched_files`
  count. Requests enqueued by earlier binaries still resume on their frozen
  schedule.
- Existing families preserve their stored reader floor. A family created by
  2.42.0 stamps `min_reader_version = 2.42.0`, so consumers must advertise
  2.42.0 reader capability when adopting this binary.
- Consumers should replace the binary; no re-extraction is needed.
