# julie-extract v2.27.0

Rebind release: the new `rebind` verb retargets an existing artifact at a new
source root by rewriting root and identity metadata only — nothing is copied,
nothing is extracted, and no extracted row is read, written, or deleted. This
is the sanctioned escape from the one-artifact-one-root gate, built for the
copy-and-rebind flow: copy an artifact to a staging path, `rebind` the copy at
the new root, then run an ordinary incremental `scan` that reconciles whatever
differs between the two checkouts. A rebind onto a byte-identical checkout
leaves that scan with nothing to do (`no_change`, zero files changed).

## The `rebind` verb

```
julie-extract rebind --root <dir> --db <path> [--strict-schema] [--json]
```

A successful retarget rewrites exactly six metadata values in one SQLite
transaction:

- `root_path` becomes the canonicalized `--root`.
- `artifact_id` becomes a freshly minted random identity, so consumers keying
  cache invalidation on `artifact_id` see the change and two artifacts rebound
  from the same copy in the same instant cannot collide.
- `updated_at` is refreshed; `created_at` is preserved — the artifact still
  dates from the extraction that built it.
- Three additive provenance keys record the retarget: `rebound_from_root`,
  `rebound_from_artifact_id`, and `rebound_at` (always equal to the refreshed
  `updated_at`). An artifact that was never rebound carries none of them.

Everything else is untouched: `binary_version`, both capability fingerprints,
the reference-resolution keys, `index_level`, every other metadata key, and
every data table. An interrupted rebind leaves the artifact either fully
retargeted or metadata-identical, never half-renamed.

## Validation gates

Each gate refuses before the next runs; a refused rebind never creates or
mutates an artifact:

- The version gates every artifact command runs (`schema_migration_required`
  under `--strict-schema`, `schema_incompatible`, `contract_incompatible`),
  reusing the same `check_versions` path as `update`.
- A capability-fingerprint mismatch fails with `fingerprint_mismatch` and exit
  code `3`: the artifact was built by a different extractor, so retargeting it
  would serve rows this binary would not produce. The fix the diagnostic names
  is a fresh `scan`.
- An artifact with no committed revision fails with the new
  `no_committed_revision` code and exit code `3`.
- The write transaction re-verifies the identity the gates validated: it
  re-reads `root_path` and `artifact_id` before writing and refuses with
  `artifact_changed` and exit code `1` if either moved — a guard for a direct
  caller racing a scan, a second rebind, or a path replacement. The write also
  opens the artifact without SQLite's create flag, so an artifact that
  vanished between validation and the write fails as `db_open_failed`, never
  as a silent re-creation.

A same-root rebind exits `0` with `changed: false` and zero metadata
mutations, byte-compared in the contract tests.

## Row-level equivalence gate

The acceptance gate is the new `rebind_equivalence` test suite: three arms
assert that a rebound-then-scanned artifact is row-level equivalent to a fresh
scan of the same root, with only the contracted identity/provenance
exclusions. Arm (a) additionally proves the post-rebind scan of a
byte-identical checkout reports `no_change`. The `rebind_contract` suite
covers the verb's argv, report shape, refusal codes, and the same-root no-op.

## Report contract

The rebind report publishes an additive top-level `rebind` object; publishing
an unknown top-level key is the report contract's sanctioned extension point,
so `report_schema_version` stays `3`. CLI contract, extraction contract,
SQLite schema, and JSONL schema are all unchanged (`1` / `4` / `5` / `4`) —
this release is purely additive.
