# julie-extract v2.30.0

v4 prerequisites release. Three producer-side changes make extraction output a
thing a store can compare, import per file, and trust as single-sourced:
`metadata_json` is now canonically serialized, so two processes over the same
tree write byte-identical text; the denormalized `identifiers.target_symbol_id`
column is gone (**SQLite schema `5` → `6`, breaking**), leaving
`identifier_resolutions` as the only place a resolution outcome lives; and the
extraction pass no longer resolves symbol references across file boundaries, so
a file extracted alone produces the same rows it produces inside a whole-repo
scan.

Extraction contract 4 and JSONL contract 4 are **unchanged**. The JSONL
identifier record still carries its `target_symbol_id` key and is byte-identical
to v2.29.0's.

Two CI gates ship with the release and exist to keep these properties from
eroding: a two-process `metadata_json` determinism contract, and an
extractor-compatibility job that byte-compares extraction output against the
previous published binary.

## Deterministic `metadata_json`

`metadata_json` is serialized from `serde_json::Value` at the CLI's single
serialization chokepoint, so keys are emitted in sorted order regardless of the
order the extractor inserted them.

Before this change, the same binary run twice over the same source tree wrote
the same key *set* in different orders. Measured across the fourteen
metadata-carrying tables, **90 of 210 metadata-carrying rows differed between two
scan processes** — `symbols` 73 of 192, `structural_facts` 17 of 18 — while
**zero rows were present in only one artifact**. Primary keys were already
deterministic; only the serialized text wobbled.

That mattered because a consumer comparing artifacts compares that text
directly. A key-order wobble reads as a content change on every row carrying a
map with two or more keys, which is exactly the false-positive a store's
row-equivalence proof cannot tolerate.

**One-time byte churn.** On the first scan with this binary, every row whose
`metadata_json` carried 2+ keys in non-canonical order is rewritten with the same
key set in sorted order. The values are unchanged and any JSON reader is
unaffected; only a consumer byte-comparing the stored strings sees it. It happens
once, because after this release the output is already canonical.

The property is now gated rather than assumed: `determinism_contract` spawns two
independent `scan` processes over the same tree and asserts byte-identical
`metadata_json` on every carrying table, plus a second test asserting the stored
text is in canonical form. The gate asserts each carrying table is non-empty, so
coverage cannot silently narrow when extractor behavior shifts.

The fix depends on `serde_json`'s `preserve_order` feature staying off — with it
on, `serde_json::Map` is insertion-ordered and the round-trip stops sorting. The
canonical-form test catches that, and the chokepoint carries a doc comment
stating the constraint.

## Schema v6: resolution outcomes live in exactly one place

v2.9.0 added `identifiers.target_symbol_id` as a denormalized convenience beside
the `identifier_resolutions` overlay. v2.30.0 removes it.

Dropped from the schema:

- the `identifiers.target_symbol_id` column,
- its `FOREIGN KEY (target_symbol_id) REFERENCES symbols(symbol_id) ON DELETE SET NULL`,
- the `idx_identifiers_target` index.

`identifier_resolutions` is now the sole source of identifier resolution
outcomes. The four lockstep `UPDATE identifiers SET target_symbol_id = …` writes
in the resolution store are deleted, so there is no second copy to drift from the
overlay.

This is safe to do because the column was never resolver input and never carried
anything the overlay did not already have. On the real 970 MB julie-extractors
artifact (schema v5, 357,748 identifiers), 32,267 rows had a non-NULL
`identifiers.target_symbol_id` and 32,267 `identifier_resolutions` rows carried a
non-NULL target, with **zero rows where the column was set but the overlay target
was missing**.

**A v6 binary refuses a v5 artifact.** No migration engine ships. Every command
that writes into the artifact — `scan` (including `--force`), `update`, `delete`,
`rebind` — fails with exit code `3` and `code = schema_migration_required`
regardless of `--strict-schema`, reporting `required_sqlite_schema_version = 6`
against `artifact_sqlite_schema_version = 5`, and leaves the artifact
byte-unchanged. Read commands (`info`, `export`) refuse under `--strict-schema`
and otherwise still read a v5 artifact. Consumers rebuild by running a full
rescan; the write refusal is unconditional because a v6 write into v5 DDL would
stamp the current schema version onto an older shape — the mislabeled artifact
this drops the column to prevent.

**JSONL contract 4 is unbumped and the export is byte-identical.** JSONL is the
only surface that exports identifier resolution outcomes, so dropping the key
would have been a capability loss the change does not ask for. The exporter now
reads the value through a `LEFT JOIN identifier_resolutions` instead of from the
column — the same value it always wrote, since the two never disagreed. Verified
between the two binaries on the same fixture: identical key sets and
byte-identical identifier records.

### The Miller migration sequence

Miller's readers were migrated to `identifier_resolutions`-only **ahead of this
release** (miller commit `238f9a89`, branch `v1-reader-migration`): every
`COALESCE(i.target_symbol_id, ir.target_symbol_id)` and every bare
`i.target_symbol_id` read was replaced with the overlay-join equivalent.

Because the consumer moved first, the pin bump to 2.30.0 needs **no dual-schema
reader** — Miller's queries are already correct against both v5 and v6 artifacts,
so the only step at pin-bump time is the full rescan the schema refusal forces.

## Extraction no longer resolves across files

`SymbolLookup` — the structure that resolves a row's symbol references while the
artifact is written — was built **per write batch**, not per file, and leaked
repo scope two ways: the requested and local id sets accumulated across every
file in the batch, and an unresolved-id arm INNER JOINed the whole `symbols`
table, so a symbol from any earlier revision could resolve.

It is now `SymbolLookup<'a>`, borrowing its ids from a single `ArtifactFile`,
with `from_file` as its only constructor. The structure cannot physically hold
another file's ids, and the whole-table SQL arm is deleted rather than left
running with its results discarded. This makes per-file isolated extraction —
the import unit a store needs — produce the same rows as a whole-repo scan.

**Cross-file links are not lost; they move to the layer that owns them.** The
resolution store still writes `pending_relationship_resolutions` and
`identifier_resolutions`. What changed is that the *extraction* pass stops
guessing at them.

Two honest notes:

- Four writer-contract tests pinned the old batch-scoped behavior as the contract
  and were inverted, not deleted. The two relationship cases were **strengthened**
  while being inverted — each file now also carries a same-file relationship, so
  the test fails both if a cross-file link survives and if the narrowing
  over-deletes.
- On real corpora this is inert. A per-file extractor cannot mint another file's
  stable symbol id, so `map_relationships` can only ever emit same-file targets;
  the plan's corpus survey found **0 cross-file links over 703k rows**. The
  compatibility harness re-ran after the narrowing and attributed no extraction-
  output difference to it — the only difference against v2.29.0 remained the
  `metadata_json` key ordering above. On a synthetic or hand-built artifact that
  does contain cross-file links, a consumer reading `relationships` *before*
  resolution runs will now see strictly fewer rows.

## Two new CI gates

- **`determinism_contract`** (contract tier, run by the `Test contract tier` step
  of the `Fast Gates` job) — two independent scan processes, byte-compared
  `metadata_json` across every carrying table.
- **`Extractor Compatibility`** (`extractor-compat` job) — downloads the latest
  published release binary for `x86_64-unknown-linux-gnu`, scans the resolution
  fixture with it and with the current build, and byte-compares every comparable
  extraction table — including the resolution tables `identifier_resolutions`
  and `pending_resolutions`, measured byte-deterministic with no normalization. A
  difference fails the job **unless** the current version names itself in
  `docs/contracts/extraction-output-changes.md` with a stated
  `classification:` line, in which case the run reports a `NOTICE:` and exits 0.
  A bare heading without a classification does not authorize the notice path.

The gate invariant: an extractor change that alters per-version extraction output
cannot merge silently. It either byte-matches the previous release, or it is
declared. Both of this release's output changes are declared under `## 2.30.0` in
that ledger, classified `incompatible`, so this release's compat run takes the
declared-notice path rather than the failure path.

The ledger's own worked example is now fenced, so it cannot act as a live
declaration: the parser trims each line before matching headings and skips only
fenced blocks, so an indented example would have declared whichever version it
named — and, sitting above the real entries, would have shadowed them.

## Compatibility

- **SQLite schema `5` → `6` — breaking.** A v6 binary refuses to WRITE into a v5
  artifact (exit `3`, `schema_migration_required`, with or without
  `--strict-schema`); `info`/`export` refuse under `--strict-schema` only.
  Rebuild with a full rescan; there is no migration path and none is planned for
  this column.
- **Extraction contract 4 and JSONL contract 4 are unchanged.** The JSONL
  identifier record keeps its `target_symbol_id` key and is byte-identical to
  v2.29.0's output.
- **`metadata_json` values are unchanged; only key order is.** Any JSON parser
  reads the same object. A byte-comparing consumer sees a one-time rewrite of
  rows whose metadata carried 2+ keys.
- `RESOLUTION_VERSION` is unchanged. v5 and v6 resolution outcomes on the same
  fixture are identical.
- **`identifiers.target_symbol_id` is gone from SQL.** Any consumer query
  selecting it must join `identifier_resolutions` instead. Miller already has
  (see the migration sequence above).
- Extraction-pass `relationships` and identifier targets are now strictly
  same-file. No first-party corpus is affected; see the note above for the
  synthetic case.
- `drop_retired_secondary_indexes` was deliberately **not** taught
  `idx_identifiers_target`: that helper exists for indexes retired without a
  schema bump, and a v6 binary never opens an artifact that could still carry it.
