# julie-extract v2.34.1

v2.34.1 fixes a v2.34.0 regression that wedged every family store written by an
earlier binary.

## Writer open reaps retired resolution capability gaps

v2.34.0 stopped declaring the `reference_resolution.*` capability gap rows but
kept extraction epoch 1. The capability snapshot sync verifies per-epoch row
counts, so any store with pre-2.34.0 history failed every import with:

```
capability snapshot conflict for extraction epoch 1
```

Fresh stores never carried the old rows, which is why release testing passed.
A real pre-2.34.0 store (128 epoch-1 gap rows against the new 19-row snapshot)
conflicted on first contact and stayed wedged.

Writer open now deletes `reference_resolution.%` rows from
`language_capability_gaps`, the same filter exports already applied. The reap
is idempotent and runs before any snapshot sync, so:

- A pre-2.34.0 store converges on first contact with this binary.
- A store already wedged by v2.34.0 self-heals on its next writer open.
- No manual repair and no re-extract is required.

Verified end-to-end against a copy of a wedged production store: the v2.34.0
binary conflicts, this binary commits and reaps the 109 retired rows.

## Compatibility

classification: compatible

No contract changes against v2.34.0. Artifacts stay schema 7, JSONL stays
contract v5, family stores stay store schema 2, and reports are unchanged.

Consumer action: replace the v2.34.0 binary. Consumers that never ran v2.34.0
against an existing store need no other action; wedged stores recover on the
next write.
