# v2.22.0

This release adds three opt-in process-lifecycle flags to `scan` for supervisors
that run many concurrent scans on one machine: `--spool-dir`, `--progress-file`,
and `--parent-pid`. No parser, grammar, capability row, language dispatch, or
schema changed, so the 38-language inventory and every contract version are
untouched.

The flags answer a field report from a consumer running concurrent scans out of
git worktrees: the machine went into the OOM killer, every killed scan left its
extraction spool behind until roughly 130 GB had accumulated over two days of
retries, and the supervisor killed healthy long scans because it could not see
them making progress.

## Every flag is inert when absent

An invocation without a flag opens no extra file, starts no thread, and issues no
extra syscall. The artifact, the report, the exit code, and the filesystem side
effects of a flagless scan are byte-for-byte what they were in v2.21.0. Contract
tests assert this against the real binary rather than by inspection, and spool
locking and spool removal are both gated on `--spool-dir` for the same reason.

## `--spool-dir <path>`

Places this scan's extraction spool in the named directory instead of the system
temporary directory, and enables removal of spools in that directory that no live
scan owns. The directory is created when missing.

Ownership is an advisory `File::lock` on a sibling `<spool>.lock` sentinel,
never a process-id probe: the kernel releases the lock however the owner dies,
including SIGKILL, so there is no process-id-reuse window. The lock never covers
the spool's own bytes, because file locks are mandatory on Windows and a lock
taken over the spool would fail the spool's own writer.

Only a spool with a matching locked sentinel is ever a removal candidate, so a
spool written without the flag — or by a scan whose sentinel could not be locked
— can never be removed by anyone. Removal happens under the lock that authorized
it. Directories may therefore be shared with flagless scans safely.

The resolved spool directory is excluded from discovery: spool files end in
`.jsonl`, so a `--spool-dir` inside `--root` would otherwise be extracted as
source. A spool directory that HOLDS anything other than spools and sentinels
raises a `spool_dir_excluded` warning, because that exclusion is invisible in the
counts and `--spool-dir $ROOT/src` would otherwise report a clean `ok` with an
artifact silently missing that subtree. A spool directory that could not carry an
ownership lock raises `spool_lock_unavailable`; the scan is unaffected but the
leak protection is inert for it. Both warnings ride every report the scan emits.

## `--progress-file <path>`

Appends live progress records while the scan runs, so a supervisor can tell a
healthy long scan from a wedged one during the phase before the artifact database
is opened. On a 74k-file tree that blind window is minutes long.

Append-only JSONL, at most one record per second and only when a counter actually
advanced, one unbuffered write per record. Within one scan the length never
decreases, so "the length grew" is a sound advance signal with no parsing. Full
consumer contract in [`progress-file-v1.md`](../contracts/progress-file-v1.md),
including how to read a length DECREASE (a new scan truncated the file: progress,
never a stall) and a torn trailing line.

The path must be named `.progress` or end in `.progress`, checked on the resolved
path. Creating the progress file truncates it, so without that rule
`--progress-file $ROOT/src/lib.rs` — one templating slip — would empty a source
file at argument time and still report `ok`.

The path may also not BE the artifact or either of its `-wal`/`-shm` sidecars.
That check compares **file identity, not path spelling**, on every supported
platform — device and inode on Unix, volume serial and file index on Windows via
`same-file` — so a hard link and a case-variant spelling are both refused. The
file is opened without truncating, identity is proven on the opened handle, and
only then is it truncated; a guard that ends at a path and a truncation that
starts from that path again are two operations on a name, and a name can be
re-pointed between them.

## `--parent-pid <pid>`

Aborts the scan when the named process stops being this process's parent. The
kernel is asked who the parent is NOW rather than whether a recorded id is still
alive, so process-id reuse cannot defeat it — an orphan is reparented to init, so
a recycled id can never re-become the parent.

The abort is cooperative and never calls `process::exit`, which would skip `Drop`
in every thread and leak precisely the spool `--spool-dir` exists to stop
leaking. The last abort point sits immediately before the scan's first
destructive step, so a `parent_exited` report always leaves the artifact
untouched. Reported as error code `parent_exited` with `expected_parent_pid` and
`observed_parent_pid` in `details`, exit code `1`.

`std` exposes no Windows counterpart for `parent_id`, so the watchdog is
Unix-only. The flag is accepted and ignored elsewhere rather than being a parse
error, so one caller argv works on every platform; Windows orphan containment
belongs to the supervisor's kill-on-close job object.

## Report changes

Additive only. New error code `parent_exited`; new warning codes
`spool_dir_excluded` and `spool_lock_unavailable`. Report codes serialize as
strings, so a consumer that reads `code` as an open string is unaffected. No
schema, contract, or CLI contract version changed.

## Dependencies

`same-file 1.0.6` becomes a direct dependency of `julie-extract-cli`. It was
already in the lock graph through `ignore` → `walkdir`, so the build graph, the
registry set, and the license set are unchanged.
