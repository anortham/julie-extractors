# v2.23.1

A hardening patch for v2.23.0's scale paths. A four-way cross-model adversarial
review (Codex + Grok, independently over the full v2.21.0→v2.23.0 range) found
six defects in the new code — none regressing below v2.22.0 behavior, all in
the failure paths of the machinery v2.23.0 introduced. All six are fixed here,
each with a regression test that fails on the v2.23.0 code.

## Spool integrity: fail closed, never silently short

The binary-frame spool reader treated a partial 1–3-byte length prefix, an
oversize length field, and a seek past end-of-file all as a clean end of
stream — so a truncated or corrupted multi-gigabyte spool imported as a
complete scan, committing an artifact silently missing files. The reader now
accepts exactly one clean EOF shape (zero bytes at a frame boundary), bounds
every frame at a named `MAX_FRAME_LEN` (256 MiB) before any allocation, and
validates every length against the file's remaining bytes before any seek. The
writer rejects oversize frames symmetrically at write time.

The spool↔snapshot completeness check was a `debug_assert` in the CLI — absent
from release builds. The import now enforces spooled-count == snapshot-count in
release mode, inside the transaction, before any revision insert; a mismatch
rolls back with the new `SpoolMissingSnapshotPaths` error.

## Bulk load: a narrower gate and honest failure states

- **Eligibility is now a true first-build predicate.** v2.23.0 gated bulk load
  on the `files` table being empty, so an artifact whose file rows were all
  deleted by a prior scan — but which still carried extraction history —
  re-qualified for `journal_mode=MEMORY`/`synchronous=OFF` writes on the live
  file, where a crash could tear real data. The gate now also requires an empty
  extraction history. (This also corrects the v2.23.0 release-note wording: the
  gate was never about scan mode — the FIRST scan into an empty artifact takes
  bulk load regardless of incremental/force mode; it is excluded for `update`,
  `delete`, and any scan of an artifact with rows or history.)
- **A failed restore is no longer swallowed.** After a failed bulk-load write,
  restoring the durable journal ran as `let _ = …`; a failed restore left the
  connection with `foreign_keys=OFF` and a MEMORY journal, still accepting
  writes. It now surfaces both errors (`BulkLoadRestoreFailed`) and poisons the
  writer — every mutating entry point fails fast on a poisoned writer.
- **A committed revision is never reported as a failed write.** `finish_journal`
  ran after `COMMIT` with plain error propagation, so a post-commit restoration
  failure was indistinguishable from a write that never happened — inviting a
  consumer to discard or re-run an hour-long build. It is now the distinct
  `JournalRestoreFailedAfterCommit` (`committed() == true`), and the CLI report
  carries `"committed": true` in the diagnostic details with a message saying
  the artifact is valid and must not be discarded.

## Extraction pool: the 16 MiB stack guarantee is real

The extraction pool was built with `.build().ok()`; on failure extraction fell
back to rayon's global pool and its ~2 MiB default worker stacks — reintroducing
the stack-overflow abort v2.23.0's recursion guards were shipped to eliminate,
precisely under the resource pressure that makes pool construction fail. Pool
selection now retries single-threaded with the same 16 MiB stack, and if that
also fails the scan fails with a structured `internal_error` diagnostic instead
of running extraction on an unverified stack.

## JSONL: the code_context contract is now true for upgraded artifacts

v2.23.0 documented `identifier.code_context` as always `null`, but the exporter
emitted whatever the column held — and artifacts written by ≤2.21.0 carry
non-null values that incremental upgrades never touch. Export now emits `null`
unconditionally; the field remains in the schema.

## Contracts

- SQLite schema version unchanged (5); catalog fingerprint unchanged.
- `extract_contract_version` unchanged (4); JSONL schema unchanged (4).
- No new report codes. New `ArtifactWriteError` variants surface through the
  existing `db_write_failed`/`internal_error` codes; the committed-but-
  unfinalized case is distinguished by `"committed": true` in diagnostic
  details.
- Parser dependency pins unchanged; no language or capability changes.
