# julie-extract v2.38.1

Patch release. It fixes one store defect and cleans up the compat-check
report; extraction output is byte-identical to v2.38.0.

## Store metadata records the real extraction identity epoch

A family store's `store_meta.extraction_identity_epoch` was hardcoded to `6`
at creation while every capability row was written at epoch `7`. The epoch
bump to 7 (v2.37.1) missed the store creation path. Miller binds its
`parser_inventory`, `language_capabilities`, `language_capability_fixtures`,
and `language_capability_gaps` projections to the recorded value, so a store
created by v2.37.1 through v2.38.0 served those projections empty.

Three changes close the defect:

- Store creation records the creating binary's real extraction identity
  epoch. `StoreLayout::create` takes the epoch as a parameter.
- A store generation rewrite carries the source store's recorded epoch
  forward, and rejects a non-integer value as a validation failure.
- Every L1 capability snapshot write moves `store_meta` to the written epoch
  in the same transaction. A store stamped with the wrong epoch by an earlier
  binary heals on its next import that carries a capability snapshot.

No schema, table, or key changes: the key exists at creation as before, and
readers that require it (Miller store read sessions) keep working unchanged.

## compat-check reports the ledger, not stale epoch constants

`cargo xtask compat-check` printed hardcoded epoch numbers (5 and 6) in its
NOTICE and diff header, and its verdict carried an epoch comparison between
those two constants, which was always true and proved nothing. The verdict
now comes from the declaration ledger alone: a difference passes as a NOTICE
only when `docs/contracts/extraction-output-changes.md` declares the current
version with a valid classification. Exit codes and verdicts are unchanged.

## Compatibility

Artifacts stay schema 7, JSONL stays contract v5, family stores stay store
schema 2, store format epoch stays 1, and the extraction identity epoch stays
7. Extraction output is byte-identical to v2.38.0, so the compat ledger needs
no `## 2.38.1` entry. `EXTRACTION_CONTRACT_VERSION` is unchanged.

Consumer action: replace the binary. Existing artifacts keep working. An
existing family store corrects its recorded epoch on the next import that
carries a capability snapshot; recreating the store corrects it immediately.
