The depth case

Hand-written extractors, not query files.

Nearly every tree-sitter-based code-intelligence tool drives extraction the same way: a pack of .scm query files per language, matched against the syntax tree by the tree-sitter query engine. julie-extractors does not. Its repository contains zero query files and never invokes the query engine. Each of its 36 languages gets an imperative Rust extractor — about 125,000 lines of extraction code in total — walking the concrete syntax tree directly.

That is an unfashionable amount of code, and it was written deliberately. This page is the case for why, what it buys, and — honestly — what it costs.

What query files are good at, and where they stop

A tree-sitter query is a declarative S-expression pattern: match this node shape, capture these child nodes, tag them @function.name or @reference.call. For syntax highlighting and basic symbol listings this is a great design — compact, data-driven, easy to ship for dozens of grammars.

The ceiling appears when a tool needs meaning rather than shape. A query can capture a node; it cannot easily carry context across the tree, apply language rules, or decide anything. Concretely, patterns of this kind sit beyond what query packs express:

  • Cross-node assembly. A C# method's real signature — modifiers, generic constraints, parameter defaults, nullability — is scattered across sibling and ancestor nodes. A capture gives you one node; a signature needs an algorithm.
  • Language semantics. Whether an identifier is a declaration, a shadowing local, or a reference to an outer symbol depends on scope rules the grammar does not encode.
  • Framework conventions. services.AddScoped<IFoo, Foo>() is just a generic method call to a query. Recognizing it as a dependency-injection registration — and emitting edges to both IFoo and Foo — requires knowing the convention, handling chained receiver forms, and parsing nested generic arguments.
  • Judgment. A query cannot decline to answer. Reference resolution — deciding which declaration an identifier points at — needs the ability to say "ambiguous" and stop, which is a control-flow decision, not a pattern match.

Tools built on query packs inherit this ceiling quietly. They report symbols and name-based references, and they look complete — until an agent asks "who calls this overload?" or "which class does this route handler live in?" and the answer isn't in the data.

What imperative extraction buys

With real code walking the tree, the extractor for each language emits thirteen data domains into one versioned SQLite artifact: symbols, identifiers, relationships, pending cross-file relationships, type facts, type-argument usages, literals, source regions, doc comments, complexity metrics, structural facts, annotations, and parse diagnostics. A few examples of depth that queries do not reach:

  • Typed structural facts. Nearly 200 versioned pattern IDs across 60 fact families capture framework and document shape as data: express.route.v1, rails.resource_route.v1, django.url_pattern.v1, spring.request_mapping.v1, fastapi.include_router.v1, aspnet.minimal_api.route.v1, nextjs.file_route.v1, phoenix.route.v1, htmx.attribute.v1, alpine.directive.v1, SQL DDL/DML shapes, and more. Each is a stable, versioned contract a downstream tool can query without touching an AST.
  • Convention-aware relationships. C# DI registrations become instantiation edges (including chained builder.Services.AddScoped<T>() forms and nested generics, without a brittle method-name allowlist for identifier capture). Partial classes are linked across files. ES-module imports carry export provenance.
  • Role-aware test detection. Tests are classified by role per language rather than by a single "is a test" bit, with golden fixtures proving at least one emitted role for all 28 code languages.
  • Real signatures and docs. Symbols carry assembled signatures, doc comments (35 of 36 languages), body spans, and per-function complexity metrics — enough for an agent to reason about an API without opening the file.

Reference resolution that fails closed

The clearest payoff is reference identity. Extraction feeds a four-tier resolution chain, and every tier prefers no answer to a plausible-but-unproven one:

  • Tier 1 — local. Same-file resolution with scope awareness: a local variable_ref beats a same-named symbol in another file.
  • Tier 2 — imports. Cross-file resolution through import statements, including aliased imports — gated per language, and fail-closed: a default import without export provenance does not resolve, and cross-language import candidates are excluded.
  • Tier 3 — receiver types. Method calls resolve through the receiver's proven static type from extracted type facts; an inferred type lowers confidence instead of faking certainty.
  • Tier 4 — unique global. A last resort that only fires when exactly one compatible candidate exists in the workspace: overloads stay ambiguous, partial-class collisions stay ambiguous, and a cross-language name collision is refused rather than guessed.

The philosophy: for a coding agent, a wrong edge is worse than a missing edge. An agent that is told "ambiguous" greps and reads; an agent handed a confident wrong answer renames the wrong method. This is also why the outcome vocabulary is explicit — resolved, ambiguous, missing, unattempted — and committed as a per-language coverage artifact that CI checks strictly.

Owning grammars where the ecosystem had gaps

Depth sometimes requires owning the layer below. julie-extractors maintains pinned tree-sitter grammar forks for C#, SQL (T-SQL), and Razor — cases where upstream grammars were missing, stale, or could not represent the constructs the extractors needed. Each fork is pinned to an exact commit under a written grammar-dependency policy, so a grammar change is a reviewed event, not a floating dependency.

Keeping 36 languages honest

The obvious failure mode of hand-written breadth is uneven depth: three great languages and thirty-three that quietly lag. The repository's answer is a capability matrix with no silent cells. Every language × domain claim is either backed by golden fixture evidence or carries a recorded reason the domain does not apply to that language ("applicable closure"). Missing work cannot hide behind not_applicable, and strict gates fail CI when fixtures drift from claims: 

node scripts/language-data-quality-report.mjs --strict
node scripts/reference-resolution-coverage-report.mjs --strict

A product rule backs this up: a new extraction capability is not done until it works for every supported language, verified on a real extract — a feature that silently covers one language while looking authoritative is treated as a bug.

What it costs, honestly

The trade is real. Averaged out, each language carries roughly 3,500 lines of extraction code, all of which must track grammar updates by hand — work a query pack mostly avoids. Adding a language is days of work, not an afternoon of pattern writing. And imperative extractors can hide bugs that declarative patterns cannot, which is why the fixture and gate machinery above exists; the honesty infrastructure is part of the price.

The bet is that for agent-facing tooling the price is right. Agents act on this data — they rename, refactor, and answer questions with it. In a paired benchmark, the same agent using Miller (whose index is exactly this artifact) got 2.2× more tasks right than with grep and file reads, with a 0% vs 27% wrong-action rate — and the five tasks requiring exact symbol identity, the thing resolution tiers exist for, went 0-for-20 without the artifact.

Try it

# produce an artifact for any repo
julie-extract scan --root . --db artifact.sqlite --json

# see exactly what your languages support
julie-extract languages --json

Binaries for macOS, Linux, and Windows are on the releases page; schema contracts live in docs/contracts/. If you want the artifact with an agent interface on top — search, refs, impact, editing — that is Miller.
