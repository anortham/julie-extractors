## Reviewed change and limits

Implementation commit `727e4435590b59373d97ffc9a08fac2233617a4b` makes
`StoreWriterConnection.transaction()` reserve the writer with `Immediate` before
the first read. Previously dereferencing selected rusqlite's deferred transaction.
The coordinator's actual import-quantum path calls this method.

The regression was also applied temporarily to the old 2.40.1 worktree. It failed
because the competing connection successfully inserted a row while the quantum
held only a read transaction. The fixed implementation refuses that competing
write and completes its own quantum. The temporary old-tree edit was reversed.

The implementing agent's preliminary report overstated two points. Pinned
rusqlite 0.40.0 already sets a 5000ms timeout in `src/inner_connection.rs` and
documents it in `src/busy.rs`. The explicit five-second timeout is policy
stabilization, not a measured change from zero. The final regression uses another
writer, not a checkpoint. A checkpoint-only explanation of the observed live
failure is not established. [SQLite's isolation documentation](https://www.sqlite.org/isolation.html)
describes the read-to-write snapshot race and the `BEGIN IMMEDIATE` remedy.

The tests prove the transaction correction. They do not identify the exact
competing connection during the earlier live Miller failure. Resident upgrade
completion must be verified after installed-package adoption. Reader retention,
fencing, schemas, parser output and CLI reports remain unchanged; the permanent
reader-registration writer floor remains 2.40.0.
