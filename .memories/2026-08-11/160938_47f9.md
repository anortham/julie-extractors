## Reviewed the store incremental-resolution brief against v2.31.4

### WHAT

Validated the plan's central diagnosis and reviewed its proposed store-path delta architecture against the live resolver, manifest publication, binding, GC, and base-selection code.

### WHY

The family-store adapter currently forces the shared resolver into full mode, bypassing the legacy path's shipped row-scoped work even though both paths use the same `ResolutionSession` engine.

### HOW

- Confirmed both store call sites pass `(true, true)`, `StoreScratchResolutionSession::prior_resolution_state` returns `None`, and its worklists force `effective_full=true`.
- Confirmed the legacy path already owns `resolve_delta`, name/import/receiver/module dependency expansion, crossover policy, equivalence tests, and sub-100ms scoped work.
- Found four plan gaps: manifest publication erases the current exact binding before a future `StorePriorOverlay` can use it; a change-row-only journal cannot prove range completeness; executor-specific writes miss the single `ManifestStore::publish_in_transaction` seam and risk omissions such as `from_artifact`; promoting a ready base does not rebind an already exact current view because `bind_base` returns the existing binding.
- Existing schema v2 rejects older schema versions and has no in-place migration, so a new public journal table needs an explicit shipped-store upgrade/promotion story.

### IMPACT

The plan's core algorithm remains the right direction—scope resolution, materialize a full exact oracle, and leave diff/publish semantics intact—but implementation should not start until lifecycle and migration corrections are folded into the brief.
