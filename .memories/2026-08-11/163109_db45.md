## WHY

Family-store resolution currently forces full-corpus work and bypasses the mature legacy incremental resolver. The first draft still had lifecycle gaps around reused generations, shipped schema-v2 stores, and partial-row carry-forward that could have produced an incomplete journal or incorrect exact catalog.

## HOW

- Scope history uses a non-reused transition id plus predecessor link; manifest generation is payload, not identity.
- The private `ManifestStore::publish_transaction` core atomically captures scope state/batches before invalidation for every real flip.
- Existing v2 stores receive a writer-side `ensure_resolution_scope_feature()` upgrade; promotion upgrades catalogs in a defined order.
- `resolution_scope_state` is a concrete GC root for predecessor base/delta eligibility.
- The store session ports legacy dependency closure but materializes full exact output by semantic table primary key, with scratch rows winning.
- Rebase reuses a ready exact base when available and atomically CAS-rotates the live binding to base plus empty delta.
- Tasks 1-7 remain forced-full/default-off; only Task 8 may enable scoped mode after equivalence, crash, branch, Miller replay, and performance gates.

## IMPACT

The plan is now implementation-ready and addresses the family-store bypass without changing Miller production behavior or `RESOLUTION_VERSION`. The capacity fix is integrated locally; no commits were pushed. Implementation begins with the additive lifecycle schema and mutating-open upgrade.
