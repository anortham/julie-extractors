## Performance audit: store import and export page-cache fixes

### WHAT
- `StoreWriter::l1_projection_matches_in_transaction` takes a reusable `L1ProjectionStaging` (one in-memory schema per quantum) instead of creating a full store schema per file. Executor creates it lazily per deep quantum.
- Bulk writer profile in `store/pragmas.rs` applies `bulk_cache_size_kib()` and `temp_store=MEMORY`; routine profile keeps the default 2 MB cache.
- `store export` uses `prepare_cached` for file and version-table inserts and applies the bulk cache to the target. `bulk_cache_size_kib` is now public in `julie_extract_artifact`.
- `docs/findings/2026-09-08-performance-audit.md` records the workload, every number, reverted experiments, and the unmeasured verified findings.

### WHY
- Fresh import of this repo read 21.8 GB and wrote 24.8 GB for a 1.2 GB store because each quantum opens a fresh connection with SQLite's default page cache, and the deep wave built an in-memory schema per file.

### NUMBERS (this repo, 2,316 files, 24 cores, tmpfs, median of 3)
- import 55.2 s -> 52.3 s (staging) -> 42.0 s (cache); bytes read 21.8 -> 10.2 GB.
- export 42.7 s -> 29.6 s (cached statements) -> 23.0 s (cache).
- Reverted: mmap_size (no wall gain), cached per-file write statements (paired runs 39.9 vs 40.0 s).

### DECISIONS
- Deep chunk default stays 8 (lease-safety, 5 s lease). Measured: 32 -> 33 s, 64 -> 31 s, 128 -> 27 s. Needs a product decision; pipelining extraction across quanta is the alternative.
- Containing-symbol binders bounded at ~5% scan CPU; not rewritten.

### IMPACT
- All artifact and CLI store contract tests pass; clippy clean. Uncommitted on main together with the earlier SQLite 3.53.2 bump and busy-lock fixes.
