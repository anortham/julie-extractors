## Project review follow-up: SQLite 3.53.2 floor and busy-lock reporting

### WHAT
- Bumped `rusqlite` 0.40.0 -> 0.40.2 and `libsqlite3-sys` 0.38.0 -> 0.38.2 in all three manifests and `Cargo.lock`. Bundled SQLite moved from 3.53.1 to 3.53.2.
- Added `crates/julie-extract-cli/tests/sqlite_engine_contract.rs`: fails if the bundled SQLite predates 3.53.1 (first 3.53.x with the WAL-reset corruption fix).
- `trusted_store_family` (import.rs) now sets a 5 s busy timeout and maps SQLITE_BUSY/LOCKED to the stable code `store_busy`; import and maintenance classifiers map it to class `busy`.
- Maintenance quick checks (maintenance.rs) set a 5 s busy timeout; a lock still held maps to `busy` / `maintenance_busy` instead of `internal`.
- Failed maintenance reports keep the `integrity_checks` that ran before the failure.
- Collapsed a nested `if` in consumed_attributes.rs (new clippy lint).
- `docs/contracts/cli.md` documents quick checks, their cost, and both busy codes.

### WHY
- User asked for a review and a SQLite version safe from the WAL-reset bug (fixed 3.51.3 / 3.53.0). We were already safe at 3.53.1; the update takes the newest crate and the test guards the floor.
- Code reviewer found a locked quick check reported `internal` (not retryable) and failed reports dropped the check list. Verified: root validation runs inside the inspector after quick checks, so only quick checks are listed on a quick-check failure.

### IMPACT
- Full `cargo test -p julie-extract-cli` default tier: all pass, wall 58 s. Workspace clippy clean.
- Uncommitted on main. Release notes for the next version should name `store_busy`, the quick-check entries, and SQLite 3.53.2.
