## Deep-wave prefetch pipeline implemented

**WHAT:** `StoreRequestExecutor` (crates/julie-extract-cli/src/store/executor.rs) now prefetches the next deep chunk on a spawned thread that drives the shared rayon pool (`Arc<ThreadPool>`) while the coordinator writes the current chunk. New: `DeepChunkPrefetch`, `spawn_prefetch`, `take_prefetch`, `discard_prefetch`, `extract_deep_chunk`, `pending_work`, `Drop` impl, crash boundary `deep_after_prefetch_spawned`, and `prefetched_files` on the `store_import_l3_chunk` progress payload.

**WHY:** Deep quanta serialized extraction and write; the pool idled during writes. Plan: docs/plans/2026-09-08-deep-wave-prefetch-pipeline.md.

**HOW:**
- Prefetch key = (request_id, chunk_index, blake3 of payload_json). Mismatch → join, discard, extract inline.
- Prefetch only starts from a deep quantum (never during the L1 wave) so the L1 publish hook test `source_change_between_waves_...` keeps seeing source changes.
- Progress counters advance at consume time, so a dropped prefetch never counts.
- Any quantum error discards the prefetch; executor Drop joins it.
- Tests: 3 contract tests in store_import_contract.rs (consumed, changed file seen by prefetch → changed_between_waves, crash after spawn resumes) + unit test for the key gate.

**IMPACT:** Paired fresh full import on this repo: median 32.6 s → 28.3 s (low load), 34.7 → 30.0 s (high load). Peak RSS unchanged (~1.95 GB). Recorded as section 6 in docs/findings/2026-09-08-performance-audit.md. All store suites pass (import 47, equivalence 7, operations 31, mixed 6, lib 167, artifact crash 11).
