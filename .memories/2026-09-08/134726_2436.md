## Fixed post-commit store-report race

### WHAT

- Added a deterministic regression in `crates/julie-extract-cli/src/store/import.rs` that holds a successor writer lock after a request is committed and verifies the terminal report still preserves the original request identity, manifest generation/hash/disposition, completion flags, and all row counts.
- Changed `execute_import` and shared `report_request` to populate committed reports exclusively from the coordinator request's durable `result_json`.
- Removed the now-dead `preserve_terminal_snapshot` parameter and branch from `populate_durable_projection`; that store read remains only for queued, claimed, and failed progress reports.

### WHY

The live request was already committed before the caller failed. After releasing the writer lease, committed reporting reopened `gen-001/store.db` to revalidate a manifest already captured in `result_json`. A successor writer could win that window and make the successful command return `database is locked`.

### HOW

The regression first failed against the old code in 5.02 seconds with the exact `database is locked` error. The fix centralizes terminal-result decoding in `populate_committed_report`, used by both the direct import path and the generic update/delete/from-artifact reporter, so there is no post-commit store dependency.

### IMPACT

A durable commit can no longer be misreported as a failed import because another writer starts before response construction. Intentional reader admission Busy behavior and writer transaction/lease policy are unchanged.
