## Extended multi-row `VALUES` batching to `source_regions` + `complexity_metrics`

Completed the perf batch from the GLM-review remediation plan: the three high-cardinality child tables now all use chunked multi-row `VALUES` inserts, sharing one no-box flush helper.

- **WHAT:** `insert_source_regions` (13 cols) and `insert_complexity_metrics` (20 cols) rewritten to the same chunked pattern as `structural_facts` — buffer `(row, valid_id)`, flush full chunks via a cached multi-row statement, tail via the cached single-row `params!` (so small files pay no per-row heap alloc). Added `source_regions_multi`/`source_region_chunk` and `complexity_metrics_multi`/`complexity_metric_chunk` fields to `ChildRowInserters`; `prepare()` computes both chunk sizes and prepares the multi-row statements.
- **WHY:** The original review item flagged single-row-per-execute inserts on these tables as a write-throughput bottleneck for large per-file corpora. The `structural_facts` slice already proved the pattern; this generalizes it.
- **HOW:** Introduced a shared generic `flush_chunk<'a, R, F>` that builds one `Vec<&'a dyn ToSql>` of `chunk.len() × cols` references and executes the cached multi-row statement once — no per-row boxing, no per-row allocation. Refactored `flush_structural_fact_chunk` onto it too. Centralized the `min(MAX_CHUNK, limit/cols).max(1)` cap in `chunk_size_for_columns` and the SQL building in `multi_row_insert_sql`.
- **Key gotcha:** `Vec<&dyn ToSql>` is invariant in its element lifetime, so a generic closure with independent input lifetimes fails to compile (E0621/lifetime-may-not-live-long-enough). Fixed by giving `flush_chunk` a single lifetime `'a` unifying row/file/`valid_id` refs, and iterating by INDEX (not `.iter()`) so `&chunk_valid[index]` borrows at `'a` (needed because `Option<&str>` is `Copy`, so a value-copy would dangle when the closure returns).
- **Harness:** Added `JULIE_PERF_REGIONS_PER_FILE` / `JULIE_PERF_METRICS_PER_FILE` env knobs to `tests/writer_perf.rs` so the feature-gated gate can drive the two tables through the multi-row path.

### Verification
- `cargo fmt --check` clean; `cargo clippy -D warnings` clean (default + `test-perf`).
- Default `cargo test -p julie-extract-artifact` green — incl. the `SQLITE_LIMIT_VARIABLE_NUMBER=64` writer-contract test (now exercises all three tables' limit-capping), tripwires, dedup test, `test_tiers` gate. `cargo test -p julie-extract-cli` green (33/9/33/5).
- Perf-gate A/B (100 files × 512 regions + 512 metrics, facts=0): multi-row ~104–106k child_rows/sec (981–1001ms) vs single-row ~95.5–96.4k (1078–1089ms) → **~10% throughput / ~8.5% wall-clock win**, mirroring the structural_facts result.
- No regression on default small-file corpus: 602–605ms / ~69.5k rows/sec (multi-row is a no-op below the 256-row chunk threshold).
