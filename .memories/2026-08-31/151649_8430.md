## Fixed the compat-check false epoch claims; cleaned up the release worktree

**WHAT:**
- Removed the merged `extractor-gap-closure-plans` worktree and its branch; Miller registry pruned (reclaimed ~495 MB of store sidecars).
- `xtask/src/compat.rs`: deleted the stale hardcoded epoch constants (5/6) and every code path built on them — `verdict_for_epochs`, the two `CompatReport` epoch fields, the epoch text in `render_diff`, and the unreachable epoch branch in `report_fail_reason`. Production now uses `verdict` (ledger-declaration policy). New `notice_line` helper renders the NOTICE without epoch claims.

**WHY:** The NOTICE printed "epoch 5"/"epoch 6" while the real `EXTRACTION_IDENTITY_EPOCH` is 7. The epoch condition `current > previous` compared the two constants, so the check always passed and proved nothing; the epoch-fail branch (`6 <= 5`) was unreachable. The verdict behavior is provably unchanged — with 5 < 6 permanently true, `verdict_for_epochs` always reduced to `decide(diff, declared)`.

**HOW:** TDD — rewrote `epoch_policy_tests` as `ledger_policy_tests` pinning the `verdict` policy (declared diff → Notice, undeclared → Fail, unclassified entry → Fail, identical → Pass) plus a `notice_line` wording test that failed first. End-to-end: compat-check vs the v2.37.2 binary → NOTICE with new wording, exit 0; vs the released v2.38.0 binary → 18 tables byte-identical, exit 0.

**Follow-up defect found, NOT fixed (persisted-data contract, out of quick-fix scope):** `julie-extract-artifact/src/store/layout.rs:696` writes store_meta `extraction_identity_epoch = "6"` while file versions carry epoch 7; `store_connection_contract.rs:32` pins the wrong "6". An external reader of store_meta gets a stale epoch. Needs its own task: decide the contract, bump the value or derive it, update the pinned test.

**IMPACT:** compat-check output is now honest; no gate verdict or exit code changed.
