## Fixed the store_meta extraction_identity_epoch hardcode

**WHAT:** Family stores now record the real extraction identity epoch instead of a stale hardcoded "6".
- `StoreLayout::create` and `initialize_store_database` take `extraction_identity_epoch: u32`; the CLI passes `EXTRACTION_IDENTITY_EPOCH` (7) at both production call sites (`import.rs`, `from_artifact.rs`).
- The generation rewrite path carries the source store's recorded epoch forward and rejects a non-integer value with a Validation error.
- `writer.rs`: every L1 capability snapshot sync upserts `store_meta.extraction_identity_epoch` to the written epoch in the same transaction, so pre-fix stores heal on their next import.

**WHY:** Miller binds its four capability projections (`parser_inventory`, `language_capabilities`, `language_capability_fixtures`, `language_capability_gaps`) to `store_meta.extraction_identity_epoch` via `WHERE extraction_epoch = (that value)`. Stores said 6 while rows were written at epoch 7, so Miller served EMPTY capability projections. Broken since the epoch 6→7 bump (`a3073cbd`, v2.37.1) — the bump missed `layout.rs`. Contained: the repo is not yet consumed in production.

**HOW:** TDD both behaviors: the connection contract test now creates with epoch 9 and asserts "9" (was pinned to the wrong "6"); a new writer contract test proves a snapshot write at epoch 1 moves store_meta to "1" (failed with "7" first). ~18 test files updated mechanically for the new `create` parameter.

**IMPACT / verification:** artifact 339 passed, CLI 494 passed, default suite 4398 passed, clippy 0 warnings, fmt clean. Open decision for the user: ship as v2.38.1 patch or fold into the next release — v2.37.1..v2.38.0 binaries all create mis-stamped stores.
