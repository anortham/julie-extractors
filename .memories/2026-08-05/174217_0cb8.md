## Bisected the single-file delta 81→172 ms regression: it's the workspace-wide `resolution_report`, not delta resolution

**WHAT:** Root-caused the pre-existing perf regression the delta-resolution-soundness branch surfaced. Detached-worktree probes of the unmodified harness at pinned commits (rustc 1.97.1, release, same seed), plus a report-only timing probe at the pivots.

**Measurements:**
- `2ae8029` (documented baseline): 82 ms — reproduces exactly, nothing environmental
- `6941e05~1`: 86 ms (report 69, delta ~17)
- `6941e05` "close reference resolution for Miller takeover": 146 ms (report 130, delta ~18) ← the bisected jump, single commit
- `cc50117~1`: 144 ms (flat after)
- branch head `db4e8d0`: 180 ms (report 131, delta ~49)

**WHY it matters beyond the gate:** `run_resolution` ends EVERY pass — delta included — with `resolution_store::resolution_report(tx)`, a workspace-wide UNION ALL over relationships + pending_relationships + all 92k identifiers with a 7-column GROUP BY, inside the write transaction. Miller's converge path pays this O(workspace) cost per file save; at dotnet/runtime scale (10M+ identifiers) that extrapolates to seconds per single-file update.

**HOW attributed:** the report was already 84% of the "81 ms" baseline; 6941e05's rewrite over base tables doubled it; the reference-sites era (`cc50117..a8dc664`) doubled the real delta work ~18→~41 ms (attributed by subtraction, not commit-bisected — harness couldn't seed in that span). Branch soundness fixes add ~8 ms of honest work.

**IMPACT:** The failing 150 ms ceiling gates a report benchmark, not delta resolution. Recommendation recorded: move `resolution_report` off the delta path (compute on full/on demand) → delta lands ~50 ms, under the 100 ms design target; do NOT re-baseline. Findings doc: `docs/findings/2026-08-05-single-file-delta-172ms-attribution.md` on the branch; harness comment updated beside the red assert.
