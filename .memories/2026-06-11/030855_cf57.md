## v2.3.0 vs v2.2.1 performance/size benchmark on openclaw (16k files, 13k TS)

Benchmarked release binaries of both versions scanning `~/source/openclaw` to answer "did the v2.3.0 data-quality release add perf or size regressions?"

### Results (cold scan / no-op rescan, /usr/bin/time -l)
- **Cold scan:** 40.2s → 43.7s (**+8.9% wall**, user CPU +2.5%, instructions retired +3.5%)
- **No-op rescan:** 1.68s → 1.67s — **unchanged**, hash-skip path unaffected
- **Peak RSS:** 678MB → 884MB (**+30%**)
- **symbols.db:** 1810MB → 1900MB (**+90MB, +5%**)

### Attribution
- `structural_facts` rows 56,611 → 222,469 (×3.9). Table +52MB, its indexes (`idx_structural_facts_pattern_language_path`, `idx_structural_facts_file_span`) +30MB → ~91% of total growth.
- JSON dominates new facts: 130,752 of 222k (59%), almost all `json.property.v1` (113k). Top offenders are machine-generated i18n translation-memory `ui/src/i18n/.i18n/*.tm.jsonl` files (~8.8k facts each; 10 files ≈ 86k facts ≈ 39% of all structural facts).
- `complexity_metrics` 94k → 102k rows (+2MB). All other tables byte-identical.

### Pre-existing (not new in v2.3.0)
- Artifact is 1.8GB for this repo even on v2.2.1 — `identifiers` (596MB + ~260MB indexes) and `source_regions` (173MB + ~200MB indexes) dominate.

### Bench notes
- Method: sequential runs via /tmp/julie-bench/run-bench.sh; first attempt invalid (concurrent runs + my sqlite3 checkpoint pre-created a 0-byte v230 db that scan refused with bare "failed", exit 3 — terse error UX worth improving).
