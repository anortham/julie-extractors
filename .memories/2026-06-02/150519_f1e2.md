## Finished spooled scan writer fix and rejected speculative speed tweaks

- **WHAT:** Retained the two-phase spooled scan write path for large repositories and removed the later speculative writer tuning experiments that did not improve real dogfood performance.
- **WHY:** `hermes-agent` originally hit `SQLite artifact write failed: too many SQL variables`, and the fix needed to bound memory without weakening artifact contracts. The subsequent speed squeeze had to be judged by real corpus timing, not synthetic microbenchmarks.
- **HOW:** Preserved JSONL file spooling, snapshot path validation, bounded symbol lookup, unchanged-file spooling for no-change scans, SQLite bulk pragmas, generated/oversized file exclusions, and JavaScript/TypeScript pending-call/import-binding traversal improvements. Backed out the bulk index drop/rebuild and existing-row cache experiments after Openclaw dogfood showed slower wall times.
- **IMPACT:** Large scans now complete without the SQL-variable failure or multi-gigabyte retained file vector. Real dogfood confirms fresh scans stay around 400 MB RSS and rescans avoid parser/writer churn. The remaining speed target is extractor traversal, especially TypeScript pending-call walking, rather than SQLite batching.
