## Fixed SQLite variable-limit failure and tuned large-repo scan performance

### WHAT
- Fixed the artifact writer `load_symbol_lookup` path that built one unbounded SQLite `IN (...)` query for all referenced symbols.
- Added runtime chunking based on SQLite `SQLITE_LIMIT_VARIABLE_NUMBER` and enabled rusqlite's `limits` feature.
- Added discovery hard exclusions for generated JS/TS variants and source files over 1 MiB.
- Cached line starts for body-span normalization to avoid repeated prefix scans on large files.
- Optimized JavaScript and TypeScript pending-call walks by carrying the active caller scope, visiting named children only, and avoiding per-node cursor allocation.
- Tuned path-backed SQLite writer PRAGMAs for generated bulk artifacts: WAL, synchronous NORMAL, temp_store MEMORY, and 128 MiB page cache.

### WHY
- Miller dogfood hit `too many SQL variables` scanning `hermes-agent`, which was an extractor writer batching bug, not Miller search performance.
- `openclaw` scanning was also too slow; release profiling showed the current bottleneck had moved into SQLite child-row insertion on a 12,781-file, 2.5M-row artifact.

### HOW
- Reproduced the SQL variable failure with a low SQLite variable limit test before fixing.
- Used live `openclaw` and `hermes-agent` scans plus macOS `sample` to separate extraction hot paths from SQLite write hot paths.
- Kept the changes local to artifact writing, discovery, span normalization, and JS/TS pending traversal.

### IMPACT
- `hermes-agent` release scan now completes without SQL-variable failure: status ok, 2,588 indexed files, 26.26s.
- `openclaw` release scan improved from 154.28s to 92.52s for the same 12,781 indexed files and same row counts.
- Peak `openclaw` RSS remains high and rose slightly with SQLite cache tuning, so the remaining architectural follow-up is streaming/two-phase artifact loading rather than holding all extracted rows in memory during write.
