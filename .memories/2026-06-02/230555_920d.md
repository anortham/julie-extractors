## Parallelized the extraction parse phase (rayon) — ~2x cold scan

Implemented the #1 perf win from the review: the file read+parse+map phase now runs in parallel across workers, while the SQLite write stays single-writer.

### Approach
- New `--jobs/-j <n>` flag on `scan` (0 = auto from cores, default). Threaded `scan() -> spool_discovered_files -> extract_supported_files_to_spool`.
- `extract_supported_files_to_spool` rewritten: process `targets` in **ordered chunks of 512**; each chunk's files extracted via `rayon par_iter` into a `Vec<FileOutcome>` (preserves order), then a **serial drain** in target order owns all shared mutable state (spool, profile, errors). This keeps peak RSS bounded (the spool's purpose) AND output byte-identical to sequential.
- Extracted `FileOutcome`/`FileOutcomeKind` + `compute_file_outcome` (pure, off-thread). Closure bound changed `FnMut` -> `Fn + Sync`.
- rayon confined to the cli crate; no leak into artifact/extractors.

### TDD
- RED: `extraction_runs_supported_files_concurrently_when_jobs_allow` (closure records max in-flight; sequential => 1 => failed exactly as expected).
- GREEN guards: `parallel_extraction_matches_single_threaded_reference` (byte-identical Vec<ArtifactFile>, jobs=1 vs 8, real extractor) and `parallel_spool_orders_failed_unchanged_and_changed_by_target` (failed/unchanged/changed stay in target order under 8 threads).

### Measured (24-core, release, --force)
- hermes-agent: 29.96s -> 14.77s = **2.03x**, row counts identical.
- openclaw: 82.47s -> 40.13s = **2.06x** (42s saved), row counts identical (640,317 symbols).
- ~2x not ~24x because the serial SQLite write (~37s) is now the floor — exactly as the review predicted. Next perf gains are in the write path (spool deserialized 4x, etc.).
