## Backend HTTP boundary coverage plan written

**WHAT:** Wrote the full implementation plan `docs/plans/2026-07-02-backend-http-boundary-coverage.md` plus decision doc `docs/decisions/0004-http-boundary-join-contract.md` for the next lane after v2.6.1.

**WHY:** User chose the next direction: extend HTTP boundary facts to all six backend ecosystems in one lane (both sides of the join), because the julie-extractors→Miller update loop is slow and small slices don't pay. Miller-side consumption of 2.6.1 is running in a parallel session.

**Scope decided (user-confirmed):**
- Handlers: Express+Fastify, FastAPI+Flask+Django, Spring (Java), Go net/http+gin+echo, Rails. C# already done.
- Clients: `http.client_request.v1` extended to python (requests/httpx), csharp (HttpClient), go (net/http), java (java.net.http), ruby (Net::HTTP).
- Top frameworks only; long tail deferred. One release (v2.7.0) at end; per-ecosystem branch gates; Tasks 2–7 parallelizable after Task 1.

**Key design (decision doc 0004):**
- 15 new pattern ids; `normalized_route_template` (`:param` flavor) is the universal server-side join key, shared normalizer in new `base/http_boundary.rs`.
- Same-file prefixes resolve into `effective_route_template`; cross-file prefixes emit mount-fact families (express.router_mount, fastapi.include_router, flask.blueprint_registration, django.url_include).
- ASP.NET families gain optional `normalized_route_template` (compatible v1 addition).
- Task 1 splits the 1753-line `framework_structural_facts.rs` into a directory module first.

**IMPACT:** Plan ready for user review and later multi-session implementation. Codex adversarial review of the plan dispatched (in flight).
