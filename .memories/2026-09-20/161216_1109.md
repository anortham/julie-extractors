## Windows ARM64 release target, v3.1.2 prep

**WHAT**
- `.github/workflows/release-binaries.yml`: new matrix entry `os: windows-11-arm`, `target: aarch64-pc-windows-msvc`, `exe_suffix: .exe`. The zip step now keys on `runner.os == Windows` instead of `matrix.os == windows-latest`. Verify step lists both Windows targets.
- `xtask/src/release.rs`: `RELEASE_TARGETS` gains `("aarch64-pc-windows-msvc", ".exe")`, so preflight and package validation accept it (preflight now reports 5 targets, 27 inputs).
- `xtask/tests/commands_contract.rs`: workflow contract test requires `windows-11-arm` and `aarch64-pc-windows-msvc`.
- `docs/release.md`: target list says five targets and names the ARM64 one.
- Version bumped 3.1.1 -> 3.1.2 in the three crate manifests and Cargo.lock; `docs/release-notes/v3.1.2.md` written (classification: compatible, no extraction change).

**WHY**
User wants Windows ARM binaries in every release. The repo is public, so the `windows-11-arm` hosted runner costs nothing.

**HOW**
Four places knew the target list (workflow matrix, xtask table, contract test, release doc). Historical evidence lines in `docs/release.md` that say "four targets" describe past releases and were left as they are.

**IMPACT**
First real proof of the ARM64 build is the `v3.1.2` release workflow run. The local `win-test` guest is x64 and cannot build or run the ARM64 binary. Tree-sitter grammars and bundled SQLite are C code compiled by the `cc` crate; expected to work on ARM64 MSVC but unproven until CI runs.
