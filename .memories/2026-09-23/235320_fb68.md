## Rust `let` type inference from same-file call initializers

**WHAT:** `rust/type_facts.rs` now infers `is_inferred=1` type facts for untyped `let` bindings. The initializer can be a same-file free fn call, `Type::f()` / `Self::f()`, or `self.f()`, plus struct expressions and the existing `Type::new` fallback. `?`, `unwrap`, `expect`, and `unwrap_or*` remove one Result/Option layer. `map_err`, `ok_or*`, and `*context` keep the layer. Any other method records nothing.

**WHY:** code-kb resolves receiver calls only through type_facts. For example, `let workspace = resolve_root(..)?` at code-kb `mcp/server.rs:259` had no fact.

**HOW:**
- `ReturnTypeIndex` is built once per file in `extract_symbols`, before phase 1, because impl methods are extracted in phase 2.
- Same-named candidates must agree. Trait methods and generic returns are excluded.
- Recursion uses the traversal depth budget (a convention test enforces it).
- Same-file only, following Go's `record_inferred_value_type` pattern. Cross-file inference would break incremental scans and the rule against workspace-global resolution.

**IMPACT:**
- The code-kb rescan (scratch db) now types line 259 as `Workspace`.
- `refs nested_project_root` lists `resolve_project_root` at server.rs:275.
- 538 new Rust facts. Unresolved receiver calls dropped 193 → 142 (my query). Of the 142, 124 have expression receivers (field chains).
- Tests: 21 in `tests/rust/initializer_types.rs`. Default, golden, capability, contract, and Rust tiers, clippy, and the quality report all pass. Changes are uncommitted on main and there is no release.
