## 2.33.0 committed locally; Windows triage found 3 real product bugs behind 17 pre-existing failures

Continues `checkpoint_22e087ed`. Two commits landed on `main`, **unpushed and untagged** by instruction:
`69806591 fix(store): …` and `f8f5ea5d release: prepare julie-extract 2.33.0`. Tree clean;
`check-release-state.sh` correctly announces the in-flight release.

### The important discovery: HEAD is far redder on Windows than one test

**17 tests fail at pristine HEAD** — 11 in the workspace suite, plus **6 in `store_resolution_contract` that
`cargo test --workspace` never runs at all** because it is gated behind
`--features test-store-resolution-contract`. Only `cargo xtask test contract` reaches them. Proven
pre-existing by an isolated detached-HEAD worktree: identical failure sets in both trees.

### Three genuine product bugs (NOT test defects), each verified empirically

1. **A failed resolve leaks its scratch DB on Windows — `Drop` body runs before fields drop.**
   `ResolutionBaseWriter` (`resolution.rs:3222`) and `ResolutionScratchWriter` (`resolution_diff.rs:317`)
   own a `rusqlite::Connection` **as a field** and unlink inside the `Drop::drop` **body**. Rust runs that
   body BEFORE dropping fields, so the handle is still open. SQLite's `winOpen` requests
   `FILE_SHARE_READ | FILE_SHARE_WRITE` with **no `FILE_SHARE_DELETE`**, so `DeleteFileW` returns
   `ERROR_SHARING_VIOLATION` — and `let _ =` swallows it. Orphaned `resolve-*.db` accumulate after every
   failed resolve; the documented "leaves no artifact" guarantee is violated. **Decisive isolating control:**
   `ResolutionScratchDelta::abort()` asserts the identical `!exists()` in the same file and PASSES on
   Windows — it holds no `Connection`. Fix: swap in an in-memory placeholder before the unlink loop, the
   idiom already used 30 lines above at `resolution.rs:3421-3422`.

2. **`store import` never retries `drain`.** `import.rs:484` drains once; on `LeaseUnavailable` it drops into
   a passive observer loop (`:488-541`) that only waits for someone else, then reports
   `failure_class: request_timeout` and exits 1. **Measured: a lease free after 4.95 s still cost a
   119-second retry** (first process given `--request-timeout-seconds 120`) — which proves it never
   re-attempts, rather than merely waiting out the 5 s TTL. **Not Windows-only:** fires on Unix whenever
   liveness is not `Dead` — unreaped zombie, recycled pid, container without `ps`/`kill`.
   `update`/`delete`/`from-artifact` already do this right via `drain_when_available` (`import.rs:954-975`).
   **Trap for any fix:** a retry inherits the ORIGINAL `requester_deadline` (`coordinator.rs:621-628`
   returns the existing request), so its budget is the crashed process's remainder, not a fresh 30 s.

3. **A Windows `process_status` already ships in this repo and the lease path just doesn't use it.**
   `export.rs:1288-1301` has `#[cfg(windows)] fn process_is_alive` using `tasklist /FI "PID eq {pid}"`, while
   `coordinator.rs:2072-2075` and `watchdog.rs:147-150` return `Unknown` on all non-Unix. This is an
   inconsistency across three call sites, not a platform limit. `unsafe_code = "forbid"` is real but the CLI
   crate already pulls `same-file`/`getrandom` to reach OS APIs behind it.

### Corrections to earlier records

- **CI is NOT ubuntu-only.** `ci.yml:100-119` defines `windows-capacity-store` on `windows-latest` — but it
  runs only `capacity_tests --lib` plus the single test
  `public_store_import_reaches_the_production_executor`. A hand-maintained two-item allowlist, structurally
  the same gap as Miller's `windows-scale-smoke`.
- **The spool reaper is CORRECT on Windows** — verified by standalone replica, not inferred. A live scan's
  spool is never reaped (Windows `LockFileEx` is per-handle, giving the same `Held` verdict as `flock`) and a
  dead scan's IS reaped. Its test fails only in *setup*: it backdates via a read-only `File::open` handle,
  which cannot satisfy `SetFileTime`'s `FILE_WRITE_ATTRIBUTES`. The 130 GB-orphan incident's inverse failure
  mode is absent.
