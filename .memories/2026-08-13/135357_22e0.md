## julie-extract 2.33.0 prepared: vacuum root cause, resolve-claim reaper, contract de-flake

### WHAT

Four production changes plus a test de-flake, staged uncommitted on `main` at 2.33.0.

1. **`step_incremental_vacuum` (maintenance.rs) — the red-HEAD root cause.** `PRAGMA incremental_vacuum(N)` yields a row per reclaimed page; `Connection::execute_batch` steps a statement exactly ONCE and discards the row. So the `N` argument was inert — one call freed one page — and the surrounding loop paid a separate implicit write transaction, and an fsync under `synchronous = FULL` + `secure_delete = ON`, per page. 4,608 pages = 4,608 fsyncs = 11.3s of an 11.5s apply, which outran the 5s writer lease and failed `finish()` with `WriterLeaseLost`. Fixed by draining the statement's rows. **23.70s → 0.55s.**

2. **`claim_resolve` (coordinator.rs) — abandoned-claim reaper.** The `other_claimed` EXISTS probe returned early *before* the `eligible` rule (stale heartbeat / dead owner) at :735-740 was ever applied to the **blocking** row. So one dead `cli-*` resolve claim wedged the whole family forever via `uidx_coord_one_claimed_resolve` — and blocked `store gc`/`store repair` too, since both refuse while any request is claimed. Now the already-shipping rule is applied to the blocker, reaping it to `failed`.

3. **Heartbeat retry backoff capped** at `interval/2` so the ladder cannot outlast the lease it defends (at the 120ms lease the tests use, a flat 100ms × 3 exceeded the whole lease).

4. **Fixed a dangling `[`QuantumLeaseRenewal`]` intra-doc link** — it pointed at a deleted duplicate heartbeat and was an open invitation to re-add it.

### WHY / HOW — key corrections to the prior session's record

- **"Wall-clock sensitive" was wrong for 2 of 3 tests.** `drain_caps…` and `batch_progresses…` contain no threads/sleeps/Durations. Their real coupling was `lease_duration_ms` (real wall clock) while every other clock is an injected `TestClock`. Fixed by giving them a 600s lease — they assert ordering/quanta, never expiry.
- **`long_running_quantum…` was failing `Disconnected`, not `Timeout`.** The 2s `recv_timeout` masked it: the drain thread was erroring out *before* `execute_quantum` because its 120ms lease lapsed during start-up. Raised to 2s lease + 120s liveness guard.
- **The reaper design from the first workflow was refuted and rebuilt.** An acquire-time hook would NOT have fixed the observed incident (`execute_resolve` blocks in `claim_until_deadline` without ever acquiring). A second "reap at acquire" hook was unsound (commits on the `HeldByOther` path). No Windows PID liveness is needed after all — resolve rows heartbeat every 250ms against a 5s window, so staleness alone is a sound signal. That matters because `process_status` is `Unknown` on all non-Unix targets.
- **Disposition is `failed`, not `queued`** — verified: `reconcile` promotes from `('queued','claimed','failed')` alike, but only a terminal state lets `store gc` reclaim resolve scratch and keeps the row out of `pending_request_ids` (whose non-emptiness permanently degrades `drain`). The opposite holds for the *takeover* requeue, which touches drain-claimed kinds that get re-claimed — `queued` is correct there.
