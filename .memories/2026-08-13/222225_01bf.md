## Coordinator SQLITE_PROTOCOL fixed; release blocked by a pre-existing lease-fence flake

Work on the julie-extract 2.33.2 Windows reliability release. The release is APPROVED by the user but gated on "all is green", and it is **not green yet**.

### WHAT changed since the last checkpoint

- **New `crates/julie-extract-artifact/src/store/wal_retry.rs`** (uncommitted): one shared helper, `is_locking_protocol` + `with_locking_protocol_retry`, with 4 unit tests. 5 retries, backoff `25ms * attempt`.
- **`coordinator.rs`** (uncommitted): replaced the inline `OpenAttemptError` enum with the shared helper, and applied it to a SECOND open that had none.
- **`.github/workflows/ci.yml`** (uncommitted): added `-- --test-threads=1` to the Windows store-resolution gate.
- **`store_resolution_contract.rs`** (uncommitted): the `left unexpected state` panic now prints the crashed child's stdout/stderr.

### WHY the residual failure had a second site

After the connection-reuse commit `dd09f49a` the suite still failed about 2 in 10 with `resolve claim lost - the coordinator could not be opened: locking protocol`.

`StoreCoordinator::open_with_liveness` opens TWO databases:
1. `open_coordinator(layout.coordinator_db())` on `coord.db` - retried in the first attempt.
2. `coordinator_store_family(layout)` on **`store.db`** read-only, to read `family_id` - NOT retried.

Both render as `locking protocol`, so the message could not tell them apart. `store.db` has its own WAL and its own zero-crossings; in the hard-kill tests, killed writers churn it constantly.

The helper wraps the whole read, not just `Connection::open`: SQLite opens lazily, so the failure surfaces at the first statement - pragma config for the coordinator, the `store_meta` query for the family id.

### HOW - two false signals in my own verification, both fixed

1. **A green run that ran zero tests.** My repeat-run script omitted `--features test-store-resolution-contract`. The binary compiled with 0 tests and printed `test result: ok` 12 times. I reported that as green for about a minute. The script now asserts the expected test count.
2. **The CI gate ran the suite wrong.** The gate I added in `704f716d` omitted `--test-threads=1`, which the xtask contract tier uses and Cargo.toml documents ("each case launches an extractor subprocess"). Without it, 24 extractors run at once and the suite fails as `busy: store writer lease fencing check failed` - machine overload that looks exactly like a product defect.

### IMPACT - what is proven and what is not

PROVEN: SQLITE_PROTOCOL is gone. 10 serial runs, 24 tests each, zero occurrences of either spelling. Serial is the HARDEST configuration for this defect (it failed 3 of 3 before the fix).

NOT GREEN: a different, rarer failure remains. Isolated loop of `rebase_crash_boundaries_retry_with_one_ready_base_and_one_empty_delta`: **2 failures in 20 runs**. The captured error is from the SEED resolve, not the crashed one:

`resolution_failed: resolution publication fence was lost for "writer-lease"`

It comes from `resolve.rs:993`, the renew immediately after acquire - BEFORE the heartbeat thread starts. So the `WriterLeaseHeartbeat` I added is not the cause of this one. `git show ff8ab576:.../resolve.rs` confirms lines 922-923 of the 2.33.1 baseline are byte-identical, so the failing path is PRE-EXISTING.

What it means: `try_acquire_or_takeover` returns `Acquired { fencing_token }`, and the very next `heartbeat_lease(holder, fencing_token, now)` returns `Ok(false)` - the lease row no longer matches this holder and token, milliseconds after acquiring it against a 5s TTL. Cause unknown; do not guess it.
