## wave 8 R5+R6: a prefix macro needs a declaration, `Q_DECL_*` is blanked anywhere

Two rule fixes in `cpp/qt_macros.rs::identifier`.

- **R5 (regression):** a line-leading Qt macro with an argument list became a `Prefix` site even when an expression followed. `QT_TR_NOOP("One"),` inside an initializer list was blanked to `,`. A `Prefix` site now needs `declaration_follows`: the tail after the macro and its arguments must start with a letter or `_`. Otherwise the identifier stays.
- **R6:** a trailing `Q_DECL_*` attribute macro is mid-line, so the old prefix rules never reached it. `is_declaration_attribute_macro` now blanks any `Q_DECL_[A-Z0-9_]+` wherever it stands. `Q_DECL_EXPORT` and `Q_DECL_IMPORT` keep the `Export` handling.

**Impact:** `static const char *names[] = { QT_TR_NOOP("One"), ... }` and a multi-line `QMetaObject::invokeMethod` with `Q_ARG` lines parse again; `QString h() const Q_DECL_NOEXCEPT;`, `void f() Q_DECL_OVERRIDE;` and `X() Q_DECL_EQ_DELETE;` now report no diagnostics.

**Known leftover:** `Q_NULLPTR` alone on a line inside an initializer list is still a `Statement` site and is blanked. The array keeps a trailing comma, so both paths stay clean.
