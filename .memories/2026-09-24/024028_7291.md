## VB.NET: infer local types from same-file call initializers

- **What:** Untyped `Dim`, `Static`, and `Using r = ...` locals now get an inferred type fact (`is_inferred = true`) from the declared return type of a same-file `Function` or `Declare Function`.
- **Why:** code-kb resolves receiver calls only through type_facts. Untyped locals made it miss real callers.
- **How:** `ReturnTypeIndex` in `vbnet/type_facts.rs` is keyed by class, structure, and module block.
  - An unqualified call uses the innermost enclosing type that declares the name, then moves out. An `Inherits` clause stops the search. Module functions come last.
  - `Me.F()` and `MyClass.F()` use the class's own members. `T.F()` works on a same-file type name.
  - `Await` removes one `Task(Of T)` or `ValueTask(Of T)` layer. `ConfigureAwait` keeps the task type.
  - Same-named candidates must agree. A generic return type records nothing.
  - A local, a parameter, or the enclosing member with the called name blocks inference. A qualifier that is also an enclosing member blocks it too.
- **Evidence:** 30 unit tests in `tests/vbnet/initializer_types.rs`. Each key guard was removed as a check, and a test then failed. New golden fixture `vbnet/call_initializers`. New doc `docs/languages/vbnet.md`.
- **Corpus:** dotnet/samples and dotnet/docs VB files gave 56 new facts. I checked all 56 against their callee declarations, and 0 were wrong. Unresolved receiver calls went from 404 to 404 and from 7876 to 7875.
