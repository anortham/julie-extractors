## WHAT

Reviewed the shared extraction path without changing production files. Confirmed that `registry::extract_for_language_at` computes complexity metrics at `ExtractionLevel::Symbols`; this is intentional current behavior because `strip_to_symbols_level` preserves complexity metrics and the extraction-level contract test asserts equality with `Full`.

## WHY

Symbols-level behavior is already a tested API: it preserves complexity metrics. Function-dense files exposed a large-file extraction scaling symptom. The full complexity collector repeats root-level sibling traversal for every symbol metric, but the experiment did not establish that as the dominant wall-time cost.

## HOW

An isolated release CLI workload used one JavaScript file with N independent functions, an external SQLite destination, `--jobs 1 --level symbols`, one warm-up, then three runs per size. p95 JavaScript extraction time: N=250 53ms; 500 177ms; 1,000 708ms; 2,000 2,905ms. `collect_complexity_metrics` loops per callable, while `metric_for_scope` calls `collect_stats` from the root for each metric. A cursor range-traversal candidate reduced static sibling visits and passed focused correctness tests, but a fair N=2,000 paired release comparison (warm each binary; alternating three pairs) was flat: before 2243/2228/2205ms, after 2378/2180/2231ms. The candidate was reverted.

## IMPACT

Complexity metrics remain present at every extraction level. The cursor traversal is not retained because it did not improve the paired wall-time metric. A future dedicated profile should identify the actual dominant cost before another performance change.
